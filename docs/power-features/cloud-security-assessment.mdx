---
title: Cloud security assessment (Prowler)
description: Scan each customer's AWS accounts, Azure subscriptions, Google Cloud projects and Microsoft 365 tenant with Prowler, on demand or on a schedule, and work the findings, checks and compliance frameworks from CoPilot.
---

CoPilot scans your customers' clouds with [Prowler](https://github.com/prowler-cloud/prowler), the open-source cloud security tool. Each customer can have up to 100 **cloud accounts** (an AWS account, Azure subscriptions, a Google Cloud project or organization, a Microsoft 365 tenant). CoPilot scans them on demand or on a schedule, keeps every scan's results, and tells you what is **new** and what was **resolved** since the scan before.

The scans run in their own container, **copilot-prowler**: Prowler's official image plus a small job API. CoPilot stores the accounts, their credentials (encrypted), the scans, their checks and findings, and Prowler's HTML and CSV reports.

<Note>
  Prowler replaces Scout Suite, which earlier CoPilot releases used for this page. Scout Suite reports aren't carried over: they lived inside the backend container.
</Note>

---

## What you get

- **Every customer's cloud posture in one list**: each account's last scan, its failures by severity, what changed since the scan before and when it is scanned next. The list follows the sidebar's customer filter.
- **Findings** that failed or need a manual review, by severity, with the resource, region and Prowler's explanation. Each one is matched with the scan before, so a new failure is marked **new**, and one that disappeared counts as **resolved**.
- **Checks**: everything Prowler checked, with its description, risk, remediation and references, and the findings of any check in one click.
- **Compliance**: how each scan maps onto the frameworks Prowler supports for the provider (CIS, NIST, ISO 27001, SOC 2, PCI DSS, MITRE ATT&CK…), requirement by requirement.
- **Prowler's own reports** (HTML and CSV) for every scan, as downloads.
- **Schedules**: daily or weekly, at an hour you pick (UTC).

## Before you start (operator)

copilot-prowler is part of CoPilot's Docker Compose file. It needs two settings in CoPilot's `.env`:

<Steps>
  <Step title="A token for the runner">
    Set `PROWLER_RUNNER_TOKEN` to a random value of at least 32 characters, for example from `openssl rand -hex 32`. copilot-backend and copilot-prowler both read it; without it every scan is refused.
  </Step>
  <Step title="A key for the cloud credentials">
    Set `CLOUD_ASSESSMENT_ENCRYPTION_KEY` to a key made with:

    ```bash
    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
    ```

    It encrypts every cloud account's credential (AWS keys, client secrets, GCP key files). Without it, no cloud account can be saved.

    <Warning>
      Keep this key. A different key makes the stored credentials unreadable: each account's credential then has to be entered again.
    </Warning>
  </Step>
  <Step title="Start it">
    ```bash
    docker compose pull && docker compose up -d
    ```

    Open **Exposure → Cloud Security Assessment**: the top right shows the Prowler version once copilot-prowler answers.
  </Step>
</Steps>

Optional settings:

| Setting | Default | What it does |
|---|---|---|
| `PROWLER_MAX_CONCURRENT` | `2` | Scans that run at once. Others wait in the queue. |
| `PROWLER_SCAN_TIMEOUT` | `14400` | Seconds before a scan is stopped. An account can set its own, 5 to 720 minutes. |
| `PROWLER_RUNNER_URL` | `http://copilot-prowler:8080` | Where the backend reaches the runner. |
| `CLOUD_ASSESSMENT_KEEP_FINDINGS_SCANS` | `30` | Each account's newest completed scans that keep their findings and reports. Older scans keep their counts and checks. |
| `CLOUD_ASSESSMENT_RETENTION_DAYS` | `400` | Scans older than this are deleted. |
| `CLOUD_ASSESSMENT_MAX_FINDINGS` | `500000` | Findings stored per scan. The counts are always complete. |

copilot-prowler publishes no port: only the backend talks to it. It needs outbound access to the cloud providers' APIs.

## Add a customer's cloud account

Cloud accounts are set up on the customer: **Customers → (customer) → Data sources → Cloud Accounts → Add account** (admins). Give the account a name, pick the provider, and enter what that provider needs. The credential is **write-only**: CoPilot never shows it again, and when you edit an account, leaving a credential field empty keeps the stored one.

Read-only access is enough for every provider: Prowler only reads.

<Tabs>
  <Tab title="AWS">
    **Recommended: an IAM role with an External ID.** Prowler assumes a read-only role in the customer's account. The External ID is generated by CoPilot, one per account, and stops anyone else from pointing an account at a role they don't own.

    1. In CoPilot, add the account with **IAM role with an External ID** and the role's ARN (`arn:aws:iam::<account>:role/ProwlerScan`). Then choose how CoPilot assumes the role:
       - **An IAM user's access keys**: the long-lived keys (`AKIA…`) of an IAM user that needs nothing but `sts:AssumeRole` on the role;
       - **CoPilot's own AWS identity**, when CoPilot runs in AWS with an EC2 instance profile or ECS task role. No keys are stored.
    2. CoPilot then shows **Role setup**: in the customer's account, create a CloudFormation stack from Prowler's `prowler-scan-role.yml` template, with:
       - `ExternalId`: the one CoPilot shows (copy button);
       - `AccountId`: the 12-digit account of the identity that assumes the role. **Replace the default, `232136659152`: that is Prowler Cloud's account**;
       - `IAMPrincipal`: that identity, as `user/<name>` or `role/<name>`.
    3. If you use an IAM user's keys, give that user the `sts:AssumeRole` policy Role setup shows.
    4. Once the stack shows `CREATE_COMPLETE`, use **Test connection**.

    **Alternative: access keys.** An IAM user in the scanned account with the `SecurityAudit` and `ViewOnlyAccess` managed policies, and its long-lived access keys.

    **Regions** are optional: without any, Prowler scans every region.
  </Tab>
  <Tab title="Azure">
    An **app registration** in the customer's Entra ID with a **client secret**:

    - the **Reader** role on each subscription to scan;
    - the Microsoft Graph permissions Prowler lists for its Entra ID checks (see [Prowler's documentation](https://docs.prowler.com)).

    Prowler's script creates all of it in one go: see [Create the app registration with Prowler's script](#create-the-app-registration-with-prowlers-script) below.

    Enter the **directory (tenant) id**, the **application (client) id**, the **client secret** (its value, not its id) and, optionally, the **subscriptions** to scan (default: every subscription the app can read).

    Enter the secret's **expiry date** as Entra ID showed it: CoPilot warns from 30 days before it lapses, and flags it once it has.
  </Tab>
  <Tab title="Microsoft 365">
    An **app registration** in the customer's Entra ID with a **client secret** and the Microsoft Graph and Exchange Online permissions Prowler lists (see [Prowler's documentation](https://docs.prowler.com)). Prowler runs its Exchange and Teams checks with the same secret. Prowler's script creates all of it: see [Create the app registration with Prowler's script](#create-the-app-registration-with-prowlers-script) below.

    Enter the **directory (tenant) id**, the **application (client) id**, the **client secret**, its **expiry date**, and **one of the tenant's domains** (for example `contoso.onmicrosoft.com`), which the connection test needs.
  </Tab>
  <Tab title="Google Cloud">
    A **service account** with the **Viewer** and **Security Reviewer** roles, and one of its **JSON keys**: paste it or upload the file.

    Optionally restrict the scan to some **projects**, skip others, or give an **organization id**. Without projects, Prowler scans every project the key can read.
  </Tab>
</Tabs>

### Create the app registration with Prowler's script

For Azure and Microsoft 365, Prowler ships a script, `prowler-azure-m365-scan-identity.sh`, that creates the app registration and gives it every read-only role and permission the scans need. Run it once per customer tenant, signed in to that tenant: in **Azure Cloud Shell** (Bash), which is signed in already, or anywhere with the Azure CLI after `az login` (`az login --allow-no-subscriptions` for a tenant without Azure subscriptions).

The person who runs it needs, in the customer's tenant:

- **Privileged Role Administrator** (or Global Administrator), to grant the application permissions and assign Global Reader;
- **Application Developer** as well, if users there can't register applications;
- for Azure, **Owner** or **User Access Administrator** on each subscription or management group to scan.

<Steps>
  <Step title="Download the script for the Prowler version CoPilot runs">
    The version is at the top right of **Exposure → Cloud Security Assessment**, for example *Prowler 5.52.0*:

    ```bash
    curl -fsSLO https://raw.githubusercontent.com/prowler-cloud/prowler/5.52.0/permissions/prowler-azure-m365-scan-identity.sh
    ```
  </Step>
  <Step title="See what it would do">
    Without `--apply` it changes nothing: it prints each command it would run.

    ```bash
    # Azure: the subscriptions to scan (repeat --subscription, or use --management-group <id>)
    bash prowler-azure-m365-scan-identity.sh --azure --subscription <subscription-id> --client-secret

    # Microsoft 365
    bash prowler-azure-m365-scan-identity.sh --m365 --client-secret

    # Both, with one app registration
    bash prowler-azure-m365-scan-identity.sh --azure --subscription <subscription-id> --m365 --client-secret
    ```
  </Step>
  <Step title="Run it">
    Add `--apply` to the same command. At the end the script prints the **Tenant ID**, the **Client ID** and, only this once, the **client secret**: copy the secret then, it is stored nowhere. The secret is valid for 180 days, and the script prints the date it expires.
  </Step>
  <Step title="Add the account in CoPilot">
    Enter the tenant id, the client id, the client secret and its expiry date (for Microsoft 365, also one of the tenant's domains), then use **Test connection**.
  </Step>
</Steps>

What it sets up, all read-only:

- **Azure** (`--azure`): the **Reader** role on each subscription or management group, a custom role, **ProwlerRole**, for four App Service checks, and three Microsoft Graph permissions for the Entra ID checks. ProwlerRole can read Function App keys and App Service app settings, which may hold secrets: `--skip-custom-role` leaves it out, and those four checks don't run.
- **Microsoft 365** (`--m365`): thirteen Microsoft Graph permissions, plus **Exchange.ManageAsApp** and the **Global Reader** directory role for the checks that run through PowerShell. `--graph-only` leaves those two out, and the PowerShell checks don't run.

Use `--client-secret`, not `--certificate`: CoPilot signs in with a client secret. The script is safe to run again. If an app registration with its name (*Prowler Scan* unless you pass `--app-name`) already exists, it stops and asks for `--use-existing-app`.

**When the secret expires**, create a new one on the app registration (**Certificates & secrets → New client secret** in the Microsoft Entra admin center) and enter it, with its expiry date, on the account. The script doesn't replace the secret it created: to use it again, delete that secret first (`az ad app credential delete`), then run it with `--use-existing-app --client-secret --apply`.

Every account also has:

- **Schedule**: off, daily, or weekly on a day, at an hour UTC.
- **Enabled**: a disabled account is neither scheduled nor scanned.
- **Advanced**: Prowler checks or services to skip, and a time limit for this account's scans.

Then use **Test connection**: Prowler signs in with the credential and says whether it works, in up to two and a half minutes. A failure shows the reason and the error Prowler raised.

## Scan

**Scan now** starts a scan at once (admins and analysts). Scheduled scans start on their own. An account runs one scan at a time.

| Status | Meaning |
|---|---|
| **Queued** | Waiting for copilot-prowler (all its slots are busy, or it can't be reached yet). |
| **Starting**, **Running** | Prowler is scanning. Large accounts take from minutes to hours. |
| **Storing results** | Prowler finished; CoPilot is storing the findings and reports. |
| **Completed** | Done. |
| **Failed** | The reason is shown, with the error Prowler raised (for example, the credentials were refused). |
| **Cancelled** | Someone stopped it. |

A completed scan may say that some checks **logged an error**: usually a permission the credential lacks. Those checks' results may be missing; give the credential the permission and scan again.

## Read the results

**Exposure → Cloud Security Assessment** lists every cloud account of the customers you can see. Open one for its details, its **failures over time** (once two scans have completed: a column per scan, its failures by severity, or the same numbers as a table; click a column or a row to open that scan) and its scans, newest first; the newest completed scan opens below them, in four tabs:

- **Overview**: the share of checks passing, the failures, the findings under manual review and muted, **new failures** and **resolved** since the scan before, the failures by severity, and the worst failing checks.
- **Findings**: what failed or needs a manual review, filtered by severity, status, muted, **new since the scan before** and text. Open one for Prowler's detail, the resource and its tags, and when it was first seen.
- **Checks**: every check of the scan, failing ones first. Open one for Prowler's description, risk, remediation, references and the frameworks it maps to, and **Its findings** to see them.
- **Compliance**: every framework the scan's checks map to, with its requirements passing, failing, under manual review and not assessed. Open one for each requirement and the checks behind it.

The account, the scan, the tab and the filters are in the URL, so a link opens the same view.

A few terms:

- **New** and **resolved** compare with the account's previous completed scan, check by check. A check that couldn't run in one of the two scans (Prowler logged an error for it, or it had nothing to check) is left out of the comparison: its failures aren't counted as resolved when it didn't run, and aren't counted as new the next time it runs. A finding keeps its first-seen time across such a gap. A check that ran but couldn't read one region still counts that region's failures as resolved, so when a scan says checks logged an error, treat its resolved count with care. An account's first scan has nothing to compare with, so it says *first scan*.
- **Manual review**: a check Prowler can't decide on its own; someone has to look.
- **Muted**: findings Prowler's mutelist suppresses. They are counted apart and hidden from the findings by default.
- **Not assessed**: a requirement no check of this scan covers. Review it by hand.

**HTML report** and **CSV** download Prowler's own reports of the scan. They hold names and tags from the customer's cloud.

## Data kept

- **Credentials**: encrypted with `CLOUD_ASSESSMENT_ENCRYPTION_KEY`, never shown or logged. Deleting an account in CoPilot doesn't revoke its credential in the cloud: remove the role, user, app registration or key there too.
- **Findings and reports**: kept for each account's newest `CLOUD_ASSESSMENT_KEEP_FINDINGS_SCANS` completed scans. An older scan says *Retention removed this scan's findings and reports* and keeps its counts, checks and compliance.
- **Scans** older than `CLOUD_ASSESSMENT_RETENTION_DAYS` are deleted. Deleting an account deletes its scans.

## Troubleshooting

<AccordionGroup>
  <Accordion title="“Cloud credentials can't be saved until CLOUD_ASSESSMENT_ENCRYPTION_KEY is set”">
    Set the key in `.env` (see *Before you start*) and recreate `copilot-backend`.
  </Accordion>
  <Accordion title="“Scans need PROWLER_RUNNER_TOKEN”, or the page says copilot-prowler doesn't answer">
    Set `PROWLER_RUNNER_TOKEN` (32 characters or more) in `.env`, the same for both containers, and check that `copilot-prowler` is running (`docker compose ps`). Scans stay queued until it answers.
  </Accordion>
  <Accordion title="“The stored credential can't be decrypted … Re-enter the credential”">
    `CLOUD_ASSESSMENT_ENCRYPTION_KEY` changed since the credential was saved. Edit the account and enter the credential again.
  </Accordion>
  <Accordion title="Test connection or a scan says the credentials were refused">
    - AWS role: check the role's trust policy has the External ID CoPilot shows and the right principal, and that the identity may call `sts:AssumeRole` on the role.
    - Azure and Microsoft 365: check the tenant id, the client id and the secret's value (not its id), and that the app has its permissions, with admin consent.
    - Google Cloud: check the key hasn't been deleted and the service account still has its roles.
  </Accordion>
  <Accordion title="“The client secret has expired”">
    Microsoft Entra ID refused the Azure or Microsoft 365 client secret because it expired. Create a new secret on the app registration (**Certificates & secrets → New client secret**), then edit the account: enter the new secret and its expiry date. CoPilot warns from 30 days before an expiry date it knows.
  </Accordion>
  <Accordion title="“No AWS credentials were found”">
    The account is an IAM role assumed with **CoPilot's own AWS identity**, and Prowler found none. Either store an IAM user's access keys on the account, or run copilot-prowler on an EC2 instance with an instance profile (IMDSv2's hop limit must be at least 2 for a container to reach it).
  </Accordion>
  <Accordion title="A scan stays queued">
    copilot-prowler is running `PROWLER_MAX_CONCURRENT` scans already. The scan starts when one ends.
  </Accordion>
  <Accordion title="“CoPilot couldn't read any of copilot-prowler's findings”">
    copilot-prowler and copilot-backend are from different releases. Pull both images and recreate both containers.
  </Accordion>
</AccordionGroup>
