Navigation Performance, Measured

The report said: moving between pages takes far longer than it should, and the previous page's requests seem to keep running. That was right. The cause was not, and it only became visible by measuring — including the measurement, made last, that recalibrates every database number in this document.

The diagnosis

The reporter's hypothesis was that aborting a request in the browser does not stop the work on the server, so navigating builds a queue. True — but it was the smaller half.

The larger half was that the backend is a single process on a single event loop, and dozens of blocking calls sat inside async def handlers. A synchronous requests.get to Wazuh does not just make its own request slow; it stops every coroutine in the process until it returns. One page load could stall the loop for seconds, and every other request in flight — including the ones the new page needed — waited behind it.

That is why the first thing built was not a fix. It was instrumentation.

Measure first, and keep measuring

An event-loop lag watchdog samples every 250 ms and attributes each stall to the requests overlapping it. A timing middleware records per-endpoint latency, slow requests and client disconnects. A per-session JSONL log is written on every server start, so sessions can be compared against each other rather than against a memory. Everything in this report comes out of those files — 16 sessions, collected over two days.

The finding that recalibrates the rest

Level 2 established a number that reframed everything after it: on this machine, every statement costs ~135 ms regardless of what it does — p50 between 134.2 and 135.1 ms across five sessions and 3,681 queries, with a p95 barely above it. Not a few slow queries. A flat toll on every round-trip.

The report's open question was where that toll came from. It has an answer, and it is the most mundane one available. MYSQL_URL on this development machine points at 10.255.254.2 — a VPN subnet. A bare TCP handshake to it, no SQL involved:

TCP handshake to 10.255.254.2:3306, seven samples

min 130.9 ms · median 132.2 ms · max 161.7 ms

132 ms of network against 135 ms measured per statement. The database does its work in about 3 ms; the rest is wire. In production the topology is different — docker-compose.yml runs MySQL as copilot-mysql on the same network as the backend, where the round-trip is sub-millisecond.

This does not invalidate the work, but it does resize part of it honestly. Round-trip reduction is the right lever for any deployment with a remote database, and the savings below are real there. Against a co-located MySQL they shrink by roughly 50×:

What holds regardless of topology is the larger part of this branch: the catalog going from 247 s to 1.1 s (YAML fetched from GitHub on the request path, plus a blocked loop), the sidebar from 15 s to 2 s (fourteen external HTTP calls in sequence), server-side cancellation of abandoned requests, and the frontend abort — which is issue #1072 itself. None of those went through the database.

Frontend — cancelling on navigation

The first attempt added an AbortController per component. Testing showed it barely fired: 340 of 381 components never created one. It was replaced with a navigation-scoped signal attached in the HTTP client to every GET, reset by a router guard when the path changes. Callers can opt out with keepOnNavigation — the sidebar healthcheck and the notification poll do, because they belong to the shell rather than to the page.

Then a second report: leaving Overview immediately felt instant, leaving after a second or two stalled. The reset was in afterEach, which fires only once navigation is confirmed — after the router has fetched the target route's JS chunk. Every route here is lazily loaded, a browser allows about six concurrent connections per host, and Overview saturates them. The chunk request was queuing behind the page being left. Moving the reset to beforeEach, registered after the auth guard so a rejected navigation never triggers it, fixed it. It is path-only: views that sync filters into the query string would otherwise cancel their own in-flight request.

193 endpoint wrappers gained an optional signal. Fifteen were deliberately left out — token refresh, licence checks, 2FA and SSO status — because cancelling them mid-navigation breaks the shell rather than saving anything.

Backend — unblocking, then not doing the work at all

Level 0 moved 86 blocking call sites onto worker threads through one helper, and raised the thread limiter from 40 to 80. This is what made everything afterwards possible: concurrency, cancellation and fan-out all require the loop to reach an await.

Level 1 cancels a GET whose client has disconnected. Starlette runs a handler to completion even after the browser has gone, so a 30-second query keeps going for a user who navigated away three seconds in. Implemented as pure ASGI middleware — BaseHTTPMiddleware would have broken SSE streaming — and only for GETs: aborting a mutation would hide whether it happened without undoing it.

Levels 3 and 4 are the same idea applied twice: stop asking the database for something it already answered. The authenticated user was being looked up 214 times in a single session because FastAPI caches a dependency by callable identity and every Security(AuthHandler()…) constructs a fresh instance. Connector credentials were read 3.15 times per request, each read costing two statements because Connectors.history_logs is declared lazy="selectin" and is never read anywhere in the codebase.

The funnel I missed

The first pass at level 4 covered get_connector_info_from_db and its 89 call sites. In the next session the cache reported 5 loads while the database still counted 54 statements against that table — something else was reading it.

It was app/utils.py:get_connector_attribute: same table, same row, another 88 call sites, no cache. The nearly identical count is what hid it — I had looked for "the funnel", found one, and stopped. Both now share the same entries; the second addresses connectors by name or by id, and an id→name map keeps the two forms on one cached row.

The database, measured rather than assumed

The connection pool was never the constraint: peak checkout was 2 of 40 across every session, with no exhaustion samples. Raising it from 15 to 40 was still correct — it was the precondition for running queries concurrently — but it was not what was slow.

Sessions are not controlled experiments — durations and browsing differ, and several are short. "Blocked" is the share of total request duration attributable to loop stalls, recomputed with one formula across all sixteen. Database columns exist only from session 12, when query metrics were added.

On the tests

114 backend tests and 39 frontend tests were added; 752 and 39 pass. Each new test was checked by re-introducing the defect it describes and confirming it fails. Two did not: one asserted on cache-copy semantics along a path that was copied for an unrelated reason, and one never exercised the id→name mapping learned on load. Both were rewritten until the defect made them fail.

What remains

  • next Re-baseline against a co-located database. Everything database-shaped measured here carries 132 ms of VPN in it. Until one session is recorded with MySQL on the same host, further round-trip work would be optimising an artefact of this development machine.
  • largest remaining The integrations chain. available_integrations → available_integrations_auth_keys accounts for 147 queries, 2.7 per request — now the biggest single block, and cacheable on the same terms as the connectors.
  • by design Endpoints heavy by construction. /vulnerabilities/search scans every vulnerability document for an agent; /mitre/atomic-tests was measured at 34 s. These are endpoint design problems, not infrastructure ones.
  • low impact The tail of blocking calls. 33 requests.* calls and 27 synchronous Elasticsearch calls have not been moved. None has ever appeared at the top of the data.
