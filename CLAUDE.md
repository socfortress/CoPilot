# CLAUDE.md

Repository orientation for AI coding assistants and human contributors. The notes below capture non-obvious context that's hard to reverse-engineer from the source alone — startup ordering, tenancy invariants, and footguns that have actually caught people. If you're using a tool that prefers `AGENTS.md`, symlink it to this file.

## What this is

SOCFortress CoPilot — a "single pane of glass" SOC platform that wraps open-source security tooling (Wazuh, Graylog, Velociraptor, Cortex, Grafana, InfluxDB, Shuffle, Sublime, …) plus many commercial integrations (CrowdStrike, Carbon Black, Defender, Mimecast, Huntress, Bitdefender, Darktrace, Duo, …).

Three independent apps in one repo:

- `backend/` — Python 3.11 FastAPI (port 5000) + APScheduler
- `frontend/` — Vue 3 / Vite SOC-analyst UI (Naive UI, Pinia, Tailwind, pnpm)
- `customer-portal/` — Vue 3 / Vite end-customer UI (port 3001 in dev, separate build)

Plus `tools/remotion-*` (video generators) and `docs/` (mkdocs site, published by `docs-pages.yml`).

## Architecture

### `backend/copilot.py` startup

One FastAPI app mounts ~50 routers under `/api`. The `@app.on_event("startup")` hook runs in order:

1. (PRODUCTION env only) `create_database_if_not_exists` + `create_copilot_user_if_not_exists` — bootstraps MySQL via root creds
2. `apply_migrations()` — Alembic `upgrade head`
3. `create_buckets()` — MinIO buckets
4. `add_connectors` / `delete_connectors` — sync supported connectors into the `connectors` table
5. `create_roles`, `create_available_integrations`, `create_available_network_connectors` — seed enums
6. `ensure_admin_user`, `ensure_scheduler_user` — idempotent system users
7. `init_scheduler()` — APScheduler, started here, removed cleanly on shutdown

CORS is wide open (`allow_origins=["*"]`). Auth is per-route via `app.auth.utils.AuthHandler` (JWT). `app/middleware/exception_handlers.py` converts `HTTPException`, `RequestValidationError`, and `ValueError` into structured responses.

### Connectors vs. Integrations vs. Routers

Three sibling namespaces with distinct roles — pick the right one:

- **`app/connectors/<tool>/`** — first-party deeply-integrated tools (Wazuh indexer/manager, Graylog, Velociraptor, Cortex, Grafana, InfluxDB, Shuffle, Sublime, Portainer, Talon, event_shipper). Credentials live in the `connectors` table. The Talon connector is special — see "AI analyst pipeline" below.
- **`app/integrations/<tool>/`** — pluggable 3rd-party services (CrowdStrike, Carbon Black, Defender, Bitdefender, Mimecast, Huntress, Darktrace, Duo, Cato, Office 365, GitHub Audit, …) plus higher-level integration features (`alert_creation_settings`, `alert_escalation`, `copilot_action`, `copilot_mcp`, `copilot_searches`, `monitoring_alert`, `modules`). Auth keys are persisted per-customer (`integration_auth_keys`).
- **`app/routers/<feature>.py`** — top-level FastAPI routers that compose connectors + integrations into product features. Every router must be imported and `include_router`-ed in `copilot.py`.

### Module layout: `routes / services / schema`

Every backend module — connectors, integrations, and feature modules (`app/auth/`, `app/customers/`, `app/incidents/`, `app/network_connectors/`, …) — follows the same modular split. When adding code, keep each layer responsible for only its concern:

- **`routes/`** — FastAPI endpoints. Thin: parse/validate input, call services, shape the response. No business logic, no DB queries, no third-party SDK calls.
- **`services/`** — business logic. Talks to the DB, calls connector/integration SDKs, orchestrates work. Imported by routes and by other services.
- **`schema/`** — Pydantic / SQLModel request and response shapes. Shared between routes and services so signatures stay typed end-to-end.
- **`models/`** (when present) — SQLModel ORM tables for that module.
- **`utils/`** or `utils.py` (when present) — pure helpers with no FastAPI or DB dependency.

New modules should mirror this structure exactly — it's what the rest of the backend assumes when importing across modules and what keeps Alembic / OpenAPI generation predictable.

### Secrets that can't be rotated

`TOTP_ENCRYPTION_KEY` (Fernet, in `app/auth/services/totp.py`) — once 2FA is enrolled, rotating this key makes stored TOTP secrets unreadable. Falls back to a key derived from `JWT_SECRET`. `SSO_STATE_SECRET` similarly falls back to `JWT_SECRET`.

### AI analyst pipeline (CoPilot ↔ Talon)

The "AI Analyst" feature is a *separate service*: [talon-analyst](https://github.com/socfortress/talon-analyst), a Python service (FastAPI, Pydantic AI agents, DBOS durable workflows, Postgres) that investigates SOC alerts and answers analyst chat. It replaced the Node.js NanoClaw Talon behind the same HTTP contract, so CoPilot's connector is unchanged. CoPilot is the database of record; Talon is the AI brain. The contract and the CoPilot changes it expects are in talon-analyst's [`docs/SPEC.md`](https://github.com/socfortress/talon-analyst/blob/main/docs/SPEC.md) §5 (inbound §5.1, write-back §5.2, CoPilot changes by phase §5.3).

**Data flow** (both directions matter):

1. **CoPilot → Talon (outbound)** — `app/connectors/talon/` is a normal CoPilot connector: the `Talon` row in `connectors` holds the URL and API key (`x-api-key`). `utils/universal.py` has the GET/POST helpers and the SSE streaming POST for chat. Calls: `POST /investigate` (alert ingest as a background task, the "Investigate with AI Analyst" button, the customer portal, report replay; `202` with a `copilot-inv-<alert_id>-<ms>` job id), `POST /message` (chat, SSE; the user id is stamped from the JWT, never the body), `POST /session/reset`, `GET /status`, `GET /templates`, and the palace calls below. The chat proxy passes Talon's own short 4xx reason through as the SSE error text; any other failure gets a fixed text, never an upstream body or exception text.
2. **Talon → CoPilot (write-back)** — Talon writes through CoPilot's REST routes under `/api/ai_analyst` (`app/ai_analyst/routes/`), as a dedicated `talon-analyst` user with the analyst role, from code and typed agent output (the model never calls them): create the job, mark it running, submit the report, then the IOCs, then mark it completed or failed. Since #1219 that user is customer-scoped like any analyst, so it must be assigned every customer whose jobs it writes back. Talon's reads of alerts, assets and prior reports go through a read-only MySQL user. `ai_analyst_report.job_id` is unique: a second report for a job is a 409.

**Tenancy on these routes.** Every Talon and `/ai_analyst` route checks the tenant of the object it names: `GET /talon/jobs/{alert_id}` the alert's customer (`verify_alert_access`); the write-back POSTs the body's customer *and* that the alert, job, report or review named is that customer's; `GET /talon/status` gives a non-admin only their own conversation lane. `tests/test_talon_connector_tenant_checks.py` pins them.

**Talon v2 chat (talon-analyst M5) is behind one setting**, `talon_connector_settings` (one row per Talon connector by name; a missing row is off; `app/connectors/talon/models/talon_v2.py`). Off, every declared `/api/talon/v2/threads…` and `/api/talon/v2/chat/{thread_id}` route answers 404 `{"detail": "Not Found"}` exactly like an unknown path (a method no route declares still answers 405) (`require_talon_v2`, which raises Starlette's exception on purpose: FastAPI's goes through CoPilot's `{success, message}` handler), and v1 is untouched. `GET /talon/v2/availability` (admin/analyst) tells the UI; `GET`/`PUT /talon/v2/settings` are admin only (by the database role too, so a demoted admin's old token can't toggle it), the `PUT` audited (`connector.update`) and refused unless talon-analyst's `GET /v2/threads` answers 2xx (its 404 = its `TALON_V2_API` is off). Load-bearing:
- **Identity is five headers CoPilot computes per request** (`services/identity.py`): `X-Talon-User` = `str(user.id)`, `X-Talon-Role` = `RoleEnum(role_id).name` (one role, not the token's scopes), `X-Talon-Customers` from `get_user_accessible_customers` (`*` admin only; a code outside talon-analyst's grammar is dropped and logged), `X-Talon-Tags`/`X-Talon-Untagged` from `build_alert_query_filters`. `utils/v2_client.py` builds every upstream header from scratch: never forward a browser header to talon-analyst.
- **Refusals keep their status** (409 = a decision pending, 403 = a customer taken away) with `{"detail": refusal_reason(...) or "Talon request failed"}`, never a 200; an upstream 401 (CoPilot's API key) and no answer at all are a 502, since a 401 logs the user out. A 2xx streams through byte for byte; `V2StreamingResponse` closes the upstream however the response ends, and every proxy route closes its DB session before calling talon-analyst. The v2 client sets `trust_env=False` (no host proxy carries the key) and, like v1, doesn't verify TLS: talon-analyst belongs on a private network.
- A thread's customer is checked before talon-analyst is asked: grammar, `enforce_customer_access`, then an exact-case `customers` row. Thread ids are UUIDs. CoPilot builds the `SubmitMessage` itself; an empty message is allowed (M5-11's resume).
- `GET /talon/v2/threads/{id}/messages?limit&before` (talon-analyst M5-5t) relays a page of a thread's earlier turns as the AI SDK's `UIMessage`s, redacted by talon-analyst exactly as its stream is; only `limit` and `before` are forwarded, and its body cap is 4 MB (`MAX_MESSAGES_BODY_BYTES`; a page is about 1,000,000 characters of stored JSON). Its two 403s keep their fixed texts: the thread's customer was removed, or the caller's alert access narrowed since the thread began.
- **Frontend (M5-5b).** `views/aiAnalyst/AiAnalyst.vue` shows `components/talonChat/v2/TalonV2Chat.vue` (a thread rail, the new-thread picker over `GET /customers` plus "General (no customer data)", prefilled from the global filter, and the conversation) only when `useTalonV2Availability` says the setting is on (cached, cleared at logout), else v1's `TalonChatContainer.vue`, unchanged. History comes from the read-back route, new turns from the stream; both fold into one model (`api/talonV2Parser.ts`: `createV2Parser` on v1's SSE framing, now `api/sse-framing.ts`; `applyV2Chunk`; `fromUIMessage`), so a turn renders the same either way. Only the assistant's text goes through `Markdown`; `detail`, `errorText`, tool names and arguments are text. 409 is "waiting for a decision"; the 403s show fixed texts (`v2/notices.ts`) and disable the composer. The approval card is M5-11b's (below). Tests: `api/__tests__/talon-v2-*.spec.ts` (the golden streams copied into `api/__tests__/fixtures/talon-v2/` at every byte split), `components/talonChat/v2/__tests__/`, `views/aiAnalyst/__tests__/AiAnalyst-talon-v2.spec.ts`, `e2e-mocked/talon-v2-chat.spec.ts`.

Tests: `tests/test_talon_v2_identity.py`, `tests/test_talon_v2_proxy.py` (no network; the golden streams in `tests/fixtures/talon_v2/` and the frontend's `src/api/__tests__/fixtures/talon-v2/` are talon-analyst's `tests/contract/golden/v2_*.txt`, excluded from end-of-file-fixer because an SSE stream ends with a blank line).

**Talon v2 chat actions are proposals CoPilot approves and runs (talon-analyst M5-11a; INV-ACT-1, D46, D47)**, behind the same setting (every `/api/talon/actions…` route 404s while off, after the scope check; the job does nothing). talon-analyst's chat tools never act: a proposal is a record there, and CoPilot decides and executes it. Load-bearing:
- **The mirror** (`talon_action_request`, `models/talon_v2.py`; no FK on `customer_code`, `copilot_ref` unique) is filled **only** from talon-analyst's `GET /v2/actions/{id}`, read with a user's own identity headers (`services/talon_action_sync.py`), never from the stream or the model's text. The chat proxy's tap (`utils/approval_tap.py`) reads the forwarded bytes without changing them and, when the stream ends (a disconnect included), syncs each card's `approvalId` as the requester in a detached task; `GET /api/talon/actions/{id}` syncs on demand; archiving a thread re-syncs its pending rows. A record whose proposal changes after mirroring is `refused`.
- **Approve, in order** (`services/talon_actions.py`): refresh with the approver's headers (pending and unexpired only) → D47 by `role_id`, never the token's scopes (`endpoint-action`: admin, responder; `external-action`: admin, analyst, responder), then `enforce_customer_access`, and `_ensure_alert_access` + the alert's customer, or `enforce_hostname_access` (`services/talon_action_execution.py`) → guarded `UPDATE … WHERE state='pending'` (one run per proposal; a second approver gets 409) → the claim, posted as the approver; **only `claimed: true` runs**. A 4xx runs nothing (400/409/422 settle the row for everyone; a 403/404, this approver's own role, customers or tags, puts it back to `pending` for others to decide); no usable answer (none, a 5xx, `claimed: false`) is `claim_lost`: never run, `failed` posted (decision f) → re-checks (an `assign_alert` assignee must be one SOC user with the customer; quarantine/release under `SELECT … FOR UPDATE` on `agents`: one row for the host name by `lower()` *and* collation, its canonical client id and customer the record's, no other row claiming that client. Each locking query is an index lookup (`ix_agents_hostname` and the functional `ix_agents_lower_hostname`, `ix_agents_velociraptor_client`, migration `d5b11a2b3c4d`; keep them, or every re-check X-locks the whole table for the Velociraptor run). The lock covers the host's rows **plus the neighbouring index gaps** for the length of the run (REPEATABLE READ's next-key locks, kept on purpose: they stop a same-name insert changing the route's `.first()`), so an insert, or a `velociraptor_id` moved, right beside the host's keys waits. MariaDB and MySQL before 8.0.13 have no functional indexes: the migration skips those two with a warning, and the `lower()` lookups lock more, and the re-check waits at most 5 s for a lock (`innodb_lock_wait_timeout` for its own statements, reset before the route runs) → the existing route handler called directly under the approver (decision e: the SLA recorder, the assignment notification, `agents.quarantined` and `RESPONSE_QUARANTINE` stay in the routes) → the result posted inline 3 times, then by `invoke_talon_action_outcomes` (every minute; back-off 1 min to hourly; stops on success, on talon-analyst's "after its window" 409, or 24 h after approval as `unreported`). A row a dead request left is settled by the job without running anything, judged by `state_changed_at` (set only by state changes, so a polling card can't keep it alive): `executing` → `unreported` after the larger of 15 min and `VELOCIRAPTOR_FLOW_TIMEOUT` + 5 min, since it may have run.
- `POST …/approve` and `…/deny` name `responder` on purpose (`RESPONDER_ROUTES`). Audit: `talon_action.approve|deny|execute`. `reason`, `args` and a comment are stored and returned as sent: plain data, never markup.
- **Endpoint collections and commands (talon-analyst EA-4; D74–D79, D84)**: `collect_artifact` and `endpoint_command` are `endpoint-action`s on a host (`FLOW_ACTIONS`, inside `HOST_ACTIONS`), so D47, `enforce_hostname_access` and the `agents` re-check apply as for quarantine. `plan_for` takes exactly `{hostname, velociraptor_id, artifact_name, parameters: {"env": [{key, value}]}}` or `{hostname, velociraptor_id, artifact_name, command}`: the record's host and client, PowerShell or bash and at most 2,000 characters of plain text (no Cc but `\n`/`\t`, Cf, Cs, Zl, Zp) for a command; for a collection, an artifact in `services/talon_catalogue.py`'s `TALON_CATALOGUE` (**must match talon-analyst's `talon.endpoint_catalogue`**; only its settable parameters, every pin at its value), never a command, script, quarantine or remediation artifact, and (`require_built_in`) Velociraptor's built-in definitions in the host's org. The re-check also requires the root org, and a flow started on another client than the plan's is `failed`. The run is the routes' shared start function (`routes/artifacts.py:start_collection_as` / `start_command_as`: the host's artifact list, the analyst artifact policy, the parameter names, and `artifact.collect` / `response.command_execute` once, as the approver), which **starts the flow and doesn't wait** (no results, no MinIO upload); `/collect` and `/command` call the same function and then wait as before (`finish_artifact_collection` / `finish_remote_command`). A Talon start passes the command and parameter values **as written** (`literal_values=True`); the manual routes keep their VQL unescaping (`vql_string_literal_value`), which would run `C:\Users` as `C:Users`. The result adds `flow_id` (only in talon-analyst's `F.[A-Za-z0-9]{1,64}` form, else `failed`), `client_id` and `artifact`; a 5xx starting one is the fixed "CoPilot could not start the collection" (the start's own text names the whole request). No command text in logs or `/command`'s error detail (CoPilot's handler logs the detail): only the artifact, client and org. `talon_action.execute` stores a command as `command_sha256` and `command_length`, never its text (`audited_args`); the mirror keeps it verbatim for the card. Tests: `tests/test_talon_endpoint_actions.py`.
- **The collection start route for investigations (talon-analyst EA-4b; D77, INV-ACT-1's stated exception)**: `POST /api/artifacts/collect/start` (admin/analyst by token, then 404 while "Talon v2" is off; `routes/talon_collections.py`, `services/talon_collections.py`). talon-analyst's investigations call it as its service user, without an approval, for an auto-run artifact on the alert's own host. Body `{hostname, velociraptor_id, artifact_name, parameters: {"env": [{key, value}]} | null}`; answer `{success, message, flow_id, client_id, artifact}`, never rows: it **starts and doesn't wait** (no MinIO upload). In order: the shape (a root-org `C.`+16-hex client; `env` values short plain text, each name once; a 400 never echoes a value) → `enforce_hostname_access` → the artifact gate → a fresh transaction and `lock_and_check_host` (the EA-4 re-check without a record: one `agents` row for the name, carrying the body's client, root org, no other claimant; 409) → `start_collection_as` under the locks (the host's list, the policy, the parameter names, `artifact.collect` once with the caller as actor, EA-1's parameterized start). **The Talon service account** (`services/talon_service_account.py`: the user id recorded when the setting was saved, so a rename keeps it in; the user named by `talon_connector_settings.collect_service_username`; and always `talon-analyst`, case-insensitive, whatever its role) may start only artifacts on `collect_allowed_artifacts`, each in `talon_catalogue.TALON_AUTO_RUN` (**must match talon-analyst's `AUTO_RUN`**: nothing settable, every pin at its value; `auto_run_violation`), else 403; with the allowlist unset (null) it starts nothing. For it the auto-run gate replaces the analyst allowlist (whose upload scan refuses `TaskScheduler`/`StartupItems`, whose uploads the pins switch off) and `enforce_auto_run_definitions` applies instead: built-in definitions, and no tools, imports or elevated permissions for the artifact and its dependencies (rule 4's VQL scan isn't applied: `StartupItems`' dependency `Windows.Forensics.Lnk` calls `eval()`/`upload()` under its own parameters). What covers the VQL is the **definition pin**: the settings PUT reads each allowed artifact's and its dependencies' definitions from Velociraptor's root org afresh and stores their SHA-256s (`collect_definition_hashes`, canonical JSON of every field the policy read returns; a definition that can't be read is a 502, one the start would refuse a 400, and nothing is saved), and a start whose definitions differ, or has none stored, is a 403 until an admin reviews the change and saves again; the GET reports the hashes and `definitions_match`. talon-analyst's `check_catalogue` checks names, parameters and switches, not the VQL. The reads are cached a minute per artifact (`collection_policy.auto_run_definitions`), one read serving the pin and the definition check; its values go as written (`literal_values`). **Every other route that starts endpoint work refuses it (403)**: `/collect` (in `start_collection_as` whenever the analyst policy applies, so an approved Talon collection too), `/collect/file/agent/{id}`, `/command`, `/quarantine`, `/file-analysis/velociraptor/enumerate` and `/submit`, the agent deletes (`/agents/{id}/delete`, `/bulk/delete`, `/bulk/delete/filter`: `Server.Utils.DeleteClient`), `/copilot_mcp/query`, `/copilot_action/invoke`, and deciding a Talon action (`check_d47`); a new such route needs `Depends(refuse_talon_service_account_dependency)`. Reads stay open to it. Every refusal of `/collect/start` is a fixed text (no host, artifact or value echoed), and its start line is logged only after validation. Everyone else keeps `/collect`'s checks, plus: no command, script, quarantine or remediation artifact for any role. Every flow gets `collect_client`'s `timeout`, `cpu_limit`, `max_rows`, `max_bytes` (`FlowLimits`, numbers CoPilot formats, never request text) from `VELOCIRAPTOR_COLLECT_START_TIMEOUT` (300, at most 300), `_CPU_LIMIT` (25), `_MAX_ROWS` (10000), `_MAX_BYTES` (1048576). A 5xx starting it is the fixed "CoPilot could not start the collection"; a flow id not in `F.[A-Za-z0-9]{1,64}` form, a 502. No parameter value in a log (the started flow echoes its request, so it isn't logged either). The setting: `GET`/`PUT /api/talon/v2/settings/collections` (admin by token and `role_id`, `no-store`, audited `connector.update` with old and new), body `{"service_username": str | null, "allowed_artifacts": [names] | null}` (both every time; null = the default name, no artifacts; names outside `TALON_AUTO_RUN` are a 400); the PUT records the id of the one user with the name (`collect_service_user_id`), the GET says whether that user exists now; the recorded id is cleared when that user is deleted (`delete_user` → `forget_deleted_user`, same transaction) and at startup when no user has it any more (`recheck_recorded_user_id`, the backstop for deletions outside `delete_user`), so a reused id never gates someone else; a recorded id whose user was renamed stays gated, with a startup warning to save the setting again; startup also warns when the setting is in use and no user has the name; migration `e4b2c0d1a7f3` (four nullable columns). Tests: `tests/test_talon_collect_start.py`.
- **What CoPilot sent Talon, and automated collections bound to it (talon-analyst AP-2a; D85 (l), D86 (j))**: every `POST /investigate` writes a `talon_investigation_trigger` row first (`services/talon_triggers.py`, migration `c2a2a0b1d3e4`, with the cap table below), in a session of its own, with `source` set by the calling path, never parsed from `sender`: `pipeline` (`incident_alert.py`), `analyst` (`investigate_alert_for_user`), `portal` (`ai_requests.py`), `replay` (`replay_investigation`), the user who asked, the alert's own customer (read from its row, never the caller's; no alert, no row) and the alert's assets as they were sent (an asset added later, by anyone, is never a target). **The Talon service account can't send or create alerts**: `POST /talon/investigate`, the report replay and `POST /incidents/alerts/create/manual` and `/create/auto` refuse it (`refuse_talon_service_account_dependency`), and a record sent by it (recorded id or name) never binds (403 `SERVICE_TRIGGER`). Missing or different: a list item is dropped (counted in a warning), a drawer or stats is a 502, a forget is "unconfirmed", and a 409's `error` is shown only when it names the customer and wing. `chat` is reserved (talon-analyst matches `/v2/memory/chat/...` as chat memory first): CoPilot answers 404 for a customer called that and never asks. talon-analyst's customer codes are lowercase `[a-z0-9_.-]` (its `KG_CUSTOMER`): an upper-case code is its 400 `invalid customer_code`, relayed.
- **talon-analyst's errors:** 400 a fixed reason (relayed as `invalid`, cleaned); 404 `unknown customer` → `unknown_customer` ("no memory yet"), `drawer not found` → `not_found`, **any other 404** → `unsupported` (no memory API, or its v2 API off); 422 → 400; 502 `MemPalace request failed`; 503 `MemPalace is not configured`; 401 → 502 (never the user's session). Stats carry `complete` ("approximate" when false); a room outside the five is listed as `other` with `room_name`; assets' `iocs` is always 0 for now ("no data yet").
- **Answers:** every field copied one by one, bounded, the connector key/password and URL user-info scrubbed (`make_scrub`; drawer markdown via `make_text_scrub`, newlines kept, 100 000 chars); an id the scrubber would change is dropped. Deadlines per call (`memory_client`): stats 50 s (`STATS_SECONDS`; talon-analyst builds them within 45 s), the list, a search, a drawer, a forget and a timeline 30 s (`SLOW_SECONDS`; its 25 s), the assets list and chat memory 8 s; no redirects, `trust_env=False`, capped raw reads (2 MB), the DB session closed before Talon is asked.
- **Forget (decision 1):** `DELETE /{customer_code}/drawers/{id}` reads the drawer first and refuses (409, without asking Talon to delete) unless `forgettable is True`, its source is `review_one_off` or `chat_remember` and it isn't durable; then `DELETE` upstream with `{"actor": username}`. Every attempt that passes the scope and v2 checks is audited `talon_memory.forget` (`entity_type` `talon_memory` or `talon_chat_memory`; old value room/source/durable/filed_at, never content; an invalid id recorded as `<invalid drawer id>`; a customer code over `audit_log.customer_code`'s 50 characters named in `details` instead): `success`, `failure`, or **`unknown`** (`AuditResult.UNKNOWN`) when the DELETE timed out, since it may have happened (504 "may or may not have been forgotten"); a 2xx with an unreadable or ownerless body is audited as done, unconfirmed (502). A confirmed forget of a `review_one_off` lesson sets CoPilot's `ai_analyst_palace_lesson` rows (that `drawer_id` and `customer_code`, one-off, `ingested`) to `expired` with `expired_at`, as the sweeper does (`expire_lesson_rows`, best effort).
- **Frontend:** `components/aiAnalyst/memory/` (`TalonMemory.vue`: customer picker from `useCustomerOptions` seeded from the global filter, tiles, a growth chart in the SOC amber, labelled room/source bars that filter the list, the list with room/source/date filters, a debounced search and "Load more" by cursor, Assets with a timeline, "My chat memory"); the detail is an `NDrawer` whose markdown goes through `Markdown` with `no-images` (never bound as HTML), links to the job (`AiAnalystJob`) and alert (`IncidentManagement-Alert`), the hidden reason (the testing note, with "testing never lowers severity", only when `testing_hidden`; else talon-analyst's `why_hidden`, and the list tag "Hidden: testing" or "Recall only", `memory.ts:hiddenTag`), and Forget only when `canForget`, confirmed in an `NModal`. `api/endpoints/talonMemory.ts:memoryFailure` tells CoPilot's own "Not Found" (v2 off) from `unsupported`. Tests: `tests/test_talon_memory.py`, `components/aiAnalyst/memory/__tests__/`, `views/aiAnalyst/__tests__/AiAnalyst-memory.spec.ts`, `e2e-mocked/talon-memory.spec.ts`.

**Persisted state on the CoPilot side** lives in `app/db/universal_models.py` as the `AiAnalyst*` block — `ai_analyst_job → ai_analyst_report → ai_analyst_ioc`, plus the human-feedback tables `ai_analyst_review`, `ai_analyst_ioc_review`, and `ai_analyst_palace_lesson`. The palace-lesson table is a queue: a CoPilot async drainer POSTs queued lessons to Talon's `POST /palace/lesson` (a MemPalace write), then flips the row from `pending` → `ingested` and stores the returned `drawer_id` (up to 255 characters) for later expiry through `POST /palace/forget`. CoPilot never speaks to MemPalace directly — every palace interaction goes through Talon. See "Database structure" below for the table-level shape.

**Per-customer auto-trigger** is gated by `incident_management_ai_analyst_trigger_enabled` (one row per customer; default off). Don't fire investigations for a customer whose row is missing or `enabled=false`.

**The Customer Portal reads AI reports through its own routes, never through `/ai_analyst`.** Every route in `app/ai_analyst/routes/` is admin/analyst-scoped, and its tenant checks are customer-level only: they know nothing of the portal's tag visibility or its per-customer AI report switch. Adding `customer_user` to those scopes would therefore show a portal user reports their portal must not. The portal instead uses the auth-scope sidestep pattern (see "Detections Catalog" for the general shape): `app/customer_portal/routes/ai_reports.py` → `services/ai_reports.py` calls the ai_analyst *service* layer directly and applies the portal's own customer + tag visibility on top (`ensure_alert_visible`, `_alert_visibility_filters`). Two consequences to preserve: the portal router is **read-only but for one request** (review submission, palace lessons, replay and Talon chat stay analyst-only by construction), and `app/customer_portal/schema/ai_reports.py` is a deliberately narrower projection than `app/ai_analyst/schema/ai_analyst.py` — job ids, template names and agent error messages never reach an end customer. `tests/test_customer_portal_ai_reports_access.py` locks both in.

**A portal user can ask Talon to (re)analyse one of their alerts (#1215)**: `POST /customer_portal/ai_reports/alert/{alert_id}/investigate`, the one portal write on this surface (`services/ai_requests.py`). Opt-in twice per customer, on the same settings row: `allow_customer_requests` (only effective with `enabled` — never start an analysis the customer cannot read) and `daily_request_limit` (NULL = unlimited, counted over any 24 hours, never shown to the customer: over it, the request is refused with a message). Both are admin-only on the settings PUT, which writes only the request fields it is sent (an explicit `daily_request_limit: null` means unlimited). Things that are load-bearing:
- **Talon creates the `ai_analyst_job` row only when it picks the request up**, so `customer_portal_ai_request` (one row per accepted request, `alert_id` deliberately not an FK) is what the cooldown and the limit count and what stops a double click from starting two analyses. The checks and the insert run under `SELECT … FOR UPDATE` on the customer's settings row; the lock is released (commit) *before* the call to Talon, and the row is deleted again if Talon refuses — a failure costs the customer nothing.
- **Order of refusals** (`refusal()`, pure): not allowed 403 → an analysis pending/running for under 2 h 409 (a job stuck longer is dead, not in progress) → the last job *or* request on the alert within 30 min 429 → over the daily limit 429. The customer code comes from the alert, never the body; Talon is told `sender="customer-portal"`; Talon's error text never reaches the customer (502, generic).
- Each request leaves a comment on the alert (signed by the user, through the comments *service*, so it neither acknowledges an SLA nor hands a waiting alert back) and an `ai_analysis.request` audit event; settings changes audit as `ai_report.settings_update`.
- The portal's AI Report tab (`AiAnalysisRequestButton.vue`) confirms before sending, then refreshes every 15 s while the analysis is under way, telling "requested, not started" apart by the new job's `created_at`.

Tests: `tests/test_customer_portal_ai_requests.py` (no DB), `tests/e2e/customer_portal_ai_requests_e2e.py` (13306, Talon replaced by a recorder), `customer-portal/cypress/e2e/ai-request.cy.ts`, `frontend/e2e-mocked/ai-report-settings.spec.ts`. Same change: `POST /talon/investigate` (analyst) now checks the alert exists, belongs to one of the caller's customers and matches the body's `customer_code`; and the ingest-time trigger hands the call to Talon to a background task instead of holding ingest for up to 120 s.

**Both portal AI surfaces are gated by one per-customer switch**, `customer_portal_ai_report_settings` (hard FK to `customers.customer_code`, one row per customer). It is **opt-in** — a missing row reads as disabled, so AI-written findings are never published to an end customer without an operator decision. Operators flip it in CoPilot under *Customers → Customer → AI Report* (`PUT /customer_portal/ai_reports/settings/{customer_code}`, **admin only**; the paired GET is admin/analyst). Don't confuse it with `incident_management_ai_analyst_trigger_enabled`: that decides whether investigations *run* for a customer, this decides whether the customer gets to *read* the result — running investigations while keeping them internal is a valid configuration. Enforcement is in `services/ai_reports.py` and applies on both read paths: `_alert_visibility_filters` ANDs in the enabled-customers subquery (so the overview aggregate silently drops disabled tenants), and `get_portal_alert_analysis` short-circuits before touching a single report row. The portal asks `GET /customer_portal/ai_reports/availability` — cheap, no report data — before rendering the AI Report tab, cached per customer code in `useAiReportsAvailability` and cleared on logout (`stores/auth.ts:setLogout`), so the next user on a shared machine never inherits the previous one's answer.

### Database structure

MySQL is the primary store via async SQLAlchemy/SQLModel (`app/db/db_session.py`); SQLite fallback in `backend/settings.py`. MinIO handles object storage (`app/data_store/`). Roughly **80 SQLModel tables** spread across the codebase — the map below is the orientation aid.

**Tenancy keystone — `customers.customer_code`.** A `varchar(50)` PK on the `customers` table that is the universal tenant key. Every per-tenant feature carries it. Two enforcement levels exist in the wild and you must read carefully which one a model uses:

- **Hard FK** (`foreign_key="customers.customer_code"`) — agents, agent_vulnerabilities, vulnerability_reports, sca_reports, event_sources, enabled_dashboards, AI analyst tables, customer_notification_route, customer_shuffle_integration, github_audit_config, github_audit_report, customers_meta. Deletes/renames cascade where set up.
- **String only, no FK** — `incident_management_alert.customer_code`, `incident_management_asset.customer_code`, `incident_management_case.customer_code`, `monitoring_alerts.customer_code`, `customer_integrations.customer_code`, `customer_network_connectors.customer_code`, `custom_alert_creation_settings.customer_code`. The ingest pipeline can land alerts for codes that don't exist yet — orphaned rows are tolerated by design. Don't add a new join expecting referential integrity.

**Permissions / RBAC** (`app/auth/models/`):

- `role` — five enumerated rows: `admin=1, analyst=2, scheduler=3, customer_user=4, responder=5` (see `RoleEnum`; ids are fixed and seeded explicitly — see "Responder role" below).
- `user` — bcrypt password, FK to role.
- `user_customer_access` — M2M scoping which customers a user can see.
- `user_tag_access` + `role_tag_access` — parallel allow-list ACLs against alert tags (`incident_management_alerttag.id`). Toggled globally by the singleton `incident_management_tag_access_settings` (`enabled` flag, `untagged_alert_behavior` ∈ admin_only|visible_to_all|default_tag).
- `user_totp` — Fernet-encrypted secret + bcrypt-hashed backup codes; `last_used_at` prevents replay.
- `sso_config` (singleton id=1) — Azure / Google / Cloudflare Access JWT settings. `sso_allowed_email` is the email allowlist (admin, analyst or responder); new SSO users default to role 2 (analyst) and, having no customer, see nothing until an admin assigns some.

**Conventions worth knowing before writing migrations or queries:**

- **MinIO blob pointer pattern** — every MinIO-backed row carries `bucket_name`, `object_key`, `file_name`, `file_size`, `file_hash`, `content_type`. Instances: `agent_datastore` (`velociraptor-artifacts`), `vulnerability_reports`, `sca_reports`, `incident_management_case_datastore`, `incident_management_case_report_template_datastore`. The DB row is the manifest; the actual bytes are in MinIO.
- **M2M join-table naming** — `<entity>_to_<entity>` (`incident_management_alert_to_ioc`, `incident_management_alert_to_tag`). One exception: `incident_management_casealertlink` collapses the underscores and uses an explicit `PrimaryKeyConstraint`.
- **Snapshot vs reference** — `incident_management_case_task` rows are snapshot-copied from `_case_template_task` at apply time. `template_task_id` is documented as a *soft link, informational only* — editing the source template does not mutate existing case tasks. Same convention applies anywhere the table comments call something "snapshot at … time."
- **Idempotency via unique constraints** — `notification_dispatch_log` uses `UniqueConstraint(customer_code, alert_id, route_id, trigger)` and the dispatch service does INSERT…ON CONFLICT DO NOTHING. `ai_analyst_review` is unique on `(report_id, reviewer_user_id)`. `enabled_dashboards` on `(customer_code, event_source_id, library_card, template_id)`. Honor these — don't write upserts that conflict with their semantics.
- **Source-mapped ingest dictionaries** — the `incident_management_*fieldname` family (`fieldname`, `assetfieldname`, `timestampfieldname`, `alerttitlefieldname`, `iocfieldname`, `customercodefieldname`) maps per-source (`wazuh`, `velociraptor`, `office365`, …) field names to canonical ingest fields. New SIEM source = new rows in *all six* tables.
- **Connector credentials are global, integration auth keys are per-customer.** Connectors (`app/connectors/models.py:Connectors`) hold one row per first-party tool for the whole deployment. Integrations (`integration_auth_keys` via the subscription chain) hold one row per (customer, integration). The third axis — Shuffle — uses `customer_shuffle_integration.shuffle_org_id` as the per-customer differentiator while the deployment-wide `SHUFFLER_API_KEY` lives in the `connectors` table.
- **Customer Portal branding is two-layered and merged per field.** `customer_portal_settings` (singleton) is the *global default*; `customer_portal_branding` (one row per customer, `enabled` toggles it without discarding the stored logo) is an optional override. Resolution is field-by-field — an override that only sets a title still inherits the global logo and color — and lives solely in `app/customer_portal/services/branding.py` (`build_effective_branding`). **Never read either table directly**: the portal (`GET /customer_portal/settings/effective`, authenticated) and the PDF report theming (`customer_report_branding.resolve_theme(..., customer_code=…)`) both go through that service. The *public* `GET /customer_portal/settings` stays global-only on purpose — the login page has no authenticated customer yet. It is also **read-only and logo-free**: the default row is seeded at startup (`ensure_default_portal_settings`), and the logo (up to 5MB of base64) is served as bytes by `GET /customer_portal/settings/logo` with `ETag` + `Cache-Control`, referenced through a versioned `logo_url` (relative to the API root). The CoPilot settings editor reads the inline logo from the admin/analyst-only `GET /customer_portal/settings/global` instead. The authenticated `GET /customer_portal/settings/effective` follows suit (`to_portal_branding`): its logo comes from `GET /customer_portal/settings/effective/logo` (`Cache-Control: private`, versioned by a content hash since merged branding has no single `updated_at`), which the portal fetches through its HTTP client — an `<img>` cannot send the Bearer token — and shows as an object URL. `EffectiveBranding` itself keeps `logo_base64` for the editor and the PDF theming. A portal user scoped to more than one customer (or holding the `"*"` wildcard) resolves to the global defaults rather than picking a winner.

### SIEM Dashboards: built-in templates vs. custom ones

`Investigate → Dashboards` renders two kinds of template through **one** pipeline:

- **Built-in** — JSON files under `app/siem/dashboard_templates/<category>/`, addressed by `(library_card=<category dir>, template_id=<file stem>)`.
- **Custom** — rows in `custom_dashboard_templates` (UI-authored or imported), addressed by `(library_card="custom", template_id=<template_key>)`.

`enabled_dashboards` is the single activation table for both, so the viewer, `POST /siem/dashboards/panel-data` and the Customer Portal need no per-kind branching. **`"custom"` is a reserved `library_card` value** — `list_categories()` skips a directory with that name so the two namespaces can never collide.

Things to keep straight when touching this area:

- **`template_key` is the stable identity.** Renaming a custom dashboard's title never changes it, which is what keeps already-enabled dashboards pointing at the right template. Creation slugifies the title and suffixes on collision (`acronis_overview_2`); *import* keeps the supplied key verbatim (409 on collision unless `overwrite`) so a definition moved between deployments stays the same dashboard.
- **`custom_dashboard_templates.customer_code` is nullable and means scope**: NULL = shared with every customer, set = that tenant only. `enable_dashboard` rejects enabling a scoped template for a different customer. Narrowing a shared template back to one customer is blocked while other tenants have it enabled.
- **`enabled_dashboards.template_id` is a plain string, not an FK**, so deleting a custom template cascades nothing — `delete_custom_dashboard` deletes the dependent `enabled_dashboards` rows itself and reports the count. Leave that out and customers keep seeing dashboards that 404 on open.
- **Panel execution lives in one place**: `services/dashboards.py:execute_panels`. It is shared by panel-data (both kinds) and by the custom-dashboard *preview* endpoint, which runs an unsaved panel set so the builder shows real data — that's the reason preview and the saved dashboard can't drift.
- **Panel types are `stat | histogram | pie | bar_h | table`.** `table` is the only one that returns rows rather than aggregations (`PanelResult.columns` / `.rows`) and the only one that reads `panel.fields` (plural) instead of `panel.field`. Both dashboard viewers (frontend *and* customer-portal) render it via their own `PanelTable.vue`; adding a sixth type means touching the executor plus both viewers.
- **Custom dashboards carry a dashboard-wide `default_query`** that `execute_panels` ANDs into every panel. Built-in templates have no equivalent — don't add per-panel duplication of it.

### Detections Catalog (view layer over `rules_cache` + Wazuh)

The Detections Catalog (*Detections → Catalog* in the sidebar, `/detection-catalog` — note URL path stays singular for backward-compat; the page title is plural since the Wazuh tab was added) is a discovery surface — *not* its own data store. It is **the single feature in CoPilot that deliberately introduces no new tables, no new columns, no Alembic migrations, no schema of any kind.** Everything is in-memory caches loading from sources that already exist.

**Source caches (all in `app/integrations/copilot_searches/services/`):**

- **`rules_cache`** — CoPilot Searches rule corpus, loaded from GitHub. Each rule carries `analytic_story`, `product`, `data_source`, `mitre_attack_id`, `tactics`, `type`, `references`, …
- **`wazuh_rules_cache`** — full Wazuh Manager ruleset, loaded via one `get_wazuh_rules(limit=100000)` call. 1-hour TTL (rules change only on operator action). Graceful degradation: when Wazuh is unreachable the cache holds `unavailable_reason` and `is_available=False` so the UI can render an inline warning instead of erroring.
- **`wazuh_firing_stats_cache`** — per-rule hit counts from the Wazuh **indexer** (not manager). 15-min TTL. One ES terms aggregation per refresh buckets the last 30d of alerts by `rule.id` with **three sub-aggs**: `last_7d` (filter to 7d), `last_seen` (max of `timestamp` — gives the most recent firing per rule, rendered as relative time in the modal), and the doc_count itself (30d). ~50–100 KB of buckets, sub-second response even on 100M-doc indices. **Uses an ES-native wildcard+exclusion pattern** rather than hardcoding `wazuh-alerts-*`, because real SOCFortress deployments spread alerts across vendor-/customer-prefixed indices (`office365-<code>`, `crowdstrike-<code>`, `carbonblack-<code>`, `huntress_<code>`, ad-hoc test indices — easily 1500+ on lab clusters). The pattern is `*,-.*,-_*,-wazuh-monitoring-*,-wazuh-statistics-*,-wazuh-states-*,-wazuh-vulnerabilities-*,-security-auditlog-*` — exclusions remove Wazuh internals + Kibana/OpenSearch system indices; the `*` includes everything else. A separate `_cat/indices` call runs alongside but only to populate `resolved_indices` for debug logging — the search itself uses the pattern string. Field-name fallback chain `rule.id → rule_id → id` because the index mapping varies across versions; the winning field is sticky between refreshes. Search uses `ignore_unavailable=True` and `allow_no_indices=True` so one inaccessible index doesn't fail the whole aggregation.

- **Per-customer firing slice is NOT cached** — `fetch_firing_stats_for_customer(customer_code)` runs a fresh ES aggregation per request with an extra `term` filter on `agent_labels_customer` (or `agent.labels.customer` — both shapes tried in fallback). Reason: caching every customer × rule combo would balloon memory for customers nobody is looking at. On-demand keeps the global cache lean and the per-customer query is still sub-second. The customer field uses Graylog's flat convention (`agent_labels_customer`) by default since that's what SOCFortress's pipelines produce; falls back to the nested Wazuh-vanilla shape (`agent.labels.customer`) for stock installs.
- **`mitre_matrix`** — STIX bundle file. Resolves `mitre_attack_id` → tactic display names and powers the Coverage Gaps tab.

Consequence: refreshing CoPilot Searches refreshes the Stories surface; Wazuh rules + firing stats have their own TTL'd refresh paths. There is no migration, no new table. Aggregations (group by story, project to row shape, compute coverage gaps, format synthesized XML, …) happen *fresh on each request* inside `services/detection_catalog.py`. **If you find yourself adding a database column, schema, or migration for the catalog, stop** — that's a design violation. The catalog must remain a thin projection.

**Surfaces (browse modes):**

- **CoPilot Searches tab** (URL token still `?tab=stories` for back-compat) — CoPilot Searches rules grouped by `analytic_story` tag. Click a row → story detail page (description, member detections table, deduplicated data sources / references). The story detail is its own URL state (`?story=Foo`), not a tab.
- **Wazuh Rules tab** — flat searchable grid over the entire Wazuh ruleset (~3–5k rows). Columns: ID · Level · Description · Groups · MITRE · File · Hits 30d (with 7d sub-count) when firing stats available. Quick-filter chips **All / Top noisy (50) / Dead (level ≥7, 0 hits 30d)** for tuning workflows. Customer-scope dropdown to slice firing stats by `agent_labels_customer` (or `agent.labels.customer` — both shapes tried). Row click → modal with full meta + reconstructed `<rule>` XML + "Last fired" relative timestamp.
- **Coverage Gaps tab** — MITRE techniques no rule in either corpus addresses. Sub-techniques collapsed into parents (a hit on T1059.001 counts as coverage for T1059) — listing every sub-technique would flood the gap report.
- **Compliance tab** — Wazuh rules grouped by control IDs for a selected compliance framework (PCI DSS / HIPAA / NIST 800-53 / GDPR / TSC / GPG13). Each row shows rule count + total firing hits per control. Frameworks are statically declared in `services/detection_catalog.py:COMPLIANCE_FRAMEWORKS` — adding a new one is one row in that dict + the field already being on the cached Wazuh rules.
- **Logtest panel** (collapsible, above the Wazuh table, not its own tab) — paste a raw log line, pick a `log_format`, see which Wazuh rule fires. Wraps Wazuh's `PUT /logtest` so we get real Wazuh decoder/rule-chain behavior rather than re-implementing the engine. The panel persists the **last 5 tests** to localStorage (`detectionCatalog.logtest.history`) so analysts can click any prior paste to restore the input + format without retyping.

**Rule source XML synthesis:** The Wazuh rule detail modal renders a reconstructed `<rule id="…" level="…">…</rule>` block in the "Rule Source" section. We **don't fetch** the original `.xml` file via Wazuh's `GET /rules/files/{filename}` because (a) that endpoint returns the whole file (dozens of rules per file), requiring XML parsing to extract one, and (b) it's admin-scoped while the catalog is analyst-accessible. Synthesis from cached fields (`id`, `level`, `description`, `groups`, `mitre`, compliance arrays, the free-form `details` dict) is functionally identical and avoids both problems. See `_synthesize_rule_xml` in `services/detection_catalog.py` if you need to evolve the format.

**Auth-scope sidestep pattern** (used throughout the catalog): when a catalog route needs data from an admin-only connector route, **call the underlying service function directly** rather than proxying through the connector route. Scope checks live on the route handler (the `Security(...require_any_scope("admin"))` dependency), not on the service function. The catalog's `wazuh_rules_cache.refresh()` calls `get_wazuh_rules()` directly; the catalog's logtest calls `run_logtest()` directly; both let the catalog routes stay `admin|analyst|customer_user` while the connector routes (used for management actions like enable/disable) stay locked down. If you find yourself wanting to widen the scope on an existing connector route to feed the catalog, don't — sidestep instead.

### Exclusion rules created in-context from an alert (#934, phases 1–2)

Velociraptor Sigma exclusion rules (`incident_management_velo_sigma_exclusion`) can be drafted from the alert they should have suppressed instead of retyped under Sources. Two routes in `app/incidents/routes/incident_alert.py`, both keyed by the CoPilot alert id and tenancy-checked like `GET /incidents/alert/{id}`: `GET /incidents/alerts/alert/{alert_id}/velo-sigma/exclusion-draft` and `POST …/exclusion-dry-run`. The frontend button (`alerts/AlertCreateExclusionRuleButton.vue`, mounted in `AlertOverview.vue`) only renders on alerts tagged `sigma-alert` — the exclusion mechanism applies to nothing else, so offering it elsewhere would just 404. Things that are load-bearing:

- **The original Sigma payload only survives in the alert's comments.** The ingest writes `Velociraptor Sigma: <title> | <channel>` (or the fallback `Title:`/`Channel:` block) plus a fenced `Full Event Payload:` JSON comment; `parse_sigma_comments` reads them back, so the prefixes in `velo_sigma.py` are a contract between writer and reader. The payload comment is best-effort at ingest and has been seen missing on real alerts, which is why a meta-only alert still yields a draft (`payload_available=false`, no field candidates) rather than a 404.
- **`extract_event_fields` is the single definition of what `field_matches` can name.** Ingest-time matching, the draft's candidate list and the dry-run all use it, so a rule built from the draft can only reference fields the matcher will find. Don't reintroduce a second flattening.
- **The dry-run is the real matcher, not a client-side guess.** `VeloSigmaExclusionService.dry_run` calls `_matches_exclusion` with a throwaway `VeloSigmaExclusion` and no DB writes; "matches" means the next identical alert is suppressed. Non-matches name each failing criterion because channel/title are exact-match and the whole point is catching the off-by-one-character rule before it is saved.
- **`resolve_customer_code` replaced a hard-coded `"unknown"`.** Before, a customer-scoped rule could never match anything — and the Sources form pre-fills the customer from the global filter, so most rules were scoped. It now resolves through `agents` (Velociraptor client id, then hostname) and fails closed to `None`, which keeps customer-scoped rules non-matching for unenrolled hosts while deployment-wide rules still apply. Expect previously-dead scoped rules to start matching after this lands.

- **Provenance is two nullable FK columns plus a comment, not a join table.** `source_alert_id` / `source_case_id` on the exclusion row (`b934a1c2d3e4`, ON DELETE SET NULL — tuning outlives the alert it was written for; NULL means "created from Sources") are settable on **create only**: `VeloSigmaExclusionUpdate` has no such fields, so a PATCH cannot re-point a rule. The create route verifies the caller can see the named alert/case before accepting it, otherwise a scoped analyst could pin a rule to another tenant's alert by guessing an id. On success the service leaves an `Exclusion rule created from this alert: …` comment on the alert (best-effort, after the commit) — that comment is the reverse link an analyst sees in the timeline, and `parse_sigma_comments` ignores it by construction. The alert page lists rules via `GET …/exclusion?source_alert_id=` (`AlertExclusionRules.vue`); the rule shows a "From alert" badge; `/incident-management/exclusion-rules/new?alert_id=N` is the deep-link form of the same flow.

Tests: `tests/test_velo_sigma_exclusion_draft.py` (no DB). Phases 3–4 of #934 (case-detail entry point, Detection Catalog pivot) are not built; `source_case_id` exists so phase 3 needs no second migration.

### Multi-instance integrations (Microsoft 365 tenants per customer)

A customer may hold several Microsoft 365 tenants — an MSSP customer with subsidiaries, acquisitions or a legacy environment (#1117). Splitting them into separate CoPilot customers would fragment their incidents, assets and reporting, so a customer's configurations of the *same* integration are distinguished by **`customer_integrations.instance_name`** (mirrored on `customer_integrations_meta`).

- **NULL is the unnamed instance** every row configured before this feature carries, and it stays addressable. Compare it through `instance_name_matches()` — `column == None` renders as `= NULL` and matches nothing. `normalize_instance_name()` collapses `""`/whitespace to NULL so a form that posts an empty string lands on the same instance as one that omits it.
- **The plumbing is generic; opting an integration in is not.** `MULTI_INSTANCE_INTEGRATIONS` in `app/integrations/routes.py` (currently `{"Office365"}`) is what `check_existing_customer_integration` consults; every other integration still 400s on a second row exactly as before. Add to the set only once that integration's provisioning *and* decommission paths handle instances. `MULTI_INSTANCE_INTEGRATIONS` in `frontend/src/components/customers/integrations/utils.ts` mirrors it for the UI — the backend is what enforces it.
- **A second instance must be named**; two NULLs would be indistinguishable to every lookup downstream. Routes that take only `(customer_code, integration_name)` go through `resolve_integration_instance()`, which returns the single instance when there is one and 400s when there are several rather than acting on an arbitrary one.
- **The stream is per tenant; the index set and Grafana are per customer.** A Graylog stream rule pins one value and an AND-matched stream cannot OR several tenant IDs together, so one stream cannot serve two tenants. Everything else is shared: **Graylog refuses an index prefix that extends an existing one**, so a per-tenant `office365-<code>-<tenant>` is rejected outright against the first tenant's `office365-<code>` ("would conflict with existing index set prefix"). All of a customer's tenants therefore write into the one `office365-<code>` index set and are read through one Grafana datasource, folder and dashboard set — which is also the right answer on its own terms, since the tenants belong to one customer and every event still names its own in `data_office365_OrganizationId`. Consequences: provisioning reuses whatever `get_existing_office365_meta` finds rather than recreating it, and **deleting one tenant while a sibling is still deployed removes only that tenant's stream** (`_cleanup_integration_infrastructure(stream_only=True)`, decided by `count_other_integration_instances` — which must use `instance_name_differs`, because `column != 'x'` is NULL for the unnamed instance and would silently drop it from the count).
- **Deployment is atomic and rolls itself back.** `provision_office365` registers an undo for every externally-visible step (`_ProvisioningRollback`) and unwinds them newest-first on any failure, so a deploy either completes or leaves nothing behind. This is not cosmetic: the Wazuh `<api_auth>` block is written *before* Graylog is touched, and a leftover block made the retry impossible — `check_if_tenant_is_already_provisioned` saw the tenant in ossec.conf and refused with "already provisioned on the Wazuh manager", so the operator could neither finish nor reattempt. A rollback never removes infrastructure the run *reused* rather than created, and one failing undo does not abandon the rest.
- **Wazuh was already multi-tenant**: several `<api_auth>` blocks inside one `<office365>` block. `add_api_auth_to_office365_block` appends; `office365/services/decommission.py` removes just the matching tenant's block on delete (and drops the whole `<office365>` element when it was the last — Wazuh rejects one with no `<api_auth>`), then restarts the manager. Deleting an integration used to leave the block behind and keep the manager polling a tenant nobody could see.
- **Alert routing no longer depends on the single-tenant columns.** Office365 alerts carry the tenant GUID where every other source carries a customer code (the `incident_management_customercodefieldname` row for `office365` points at `data_office365_OrganizationId`). `custom_alert_creation_settings.office365_organization_id` and `customers_meta.customer_meta_office365_organization_id` hold one tenant each, so they are now written **only while empty** (the customer's first tenant claims them) and cleared on delete by tenant ID. Every later tenant resolves through `resolve_customer_code_from_office365_tenant()` (`office365/services/tenant_lookup.py`), which reads the `TENANT_ID` auth keys already stored per instance — **no new table**. The three call sites that consult the legacy columns first and fall back to it are `app/utils.py`, `incidents/services/incident_alert.py:is_customer_code_valid` and `integrations/monitoring_alert/routes/provision.py:get_customer_meta`.
- **`extract_office365_auth_keys` flattens every subscription's keys into one dict**, so the record handed to it must already be narrowed to one instance (`find_customer_integration(..., match_instance=True)`) — otherwise one tenant's ID is paired with another's secret.

Tests: `tests/test_office365_multi_tenant.py` (no DB, no network).

### OpenCTI connector (GraphQL foundation, #1143)

`app/connectors/opencti/` is a normal first-party connector (`OPENCTI_URL` / `OPENCTI_API_KEY`, `api_key` auth, row name `OpenCTI`) built as the base for any feature that needs threat intel from OpenCTI. Routes live under `/api/opencti` (`/about`, `/observables/search`, `/indicators`, `/entities/{id}`, admin/analyst, no tenant scoping because OpenCTI data is deployment-wide). Adding a feature means writing a query in `services/queries.py` and a service function. Don't add a transport.

- **OpenCTI reports failure as HTTP 200.** A bad token, a malformed query and a missing capability all return 200 with an `errors` array (`AUTH_REQUIRED`, `GRAPHQL_VALIDATION_FAILED`, …) and a `data` full of nulls. `send_graphql_request` treats any `errors` entry as `success=False`. A caller that checks the status code or reads `data` directly will show a revoked token as healthy.
- **Plain GraphQL over `httpx`, not `pycti`.** The SDK is synchronous and has to track the server's exact version. A GraphQL document keeps working across releases as long as the fields it names exist.
- **Lists are Relay connections.** Use `paginate_graphql(query, connection_path, …)` rather than hand-rolling a cursor loop. The query must declare `$first: Int, $after: ID` and select `pageInfo { hasNextPage endCursor }`.
- **Shared fields are GraphQL fragments** (`CoreMeta`, `IndicatorFields`). A document must define exactly the fragments it spreads, because an unused one fails server-side validation. `test_every_query_defines_exactly_the_fragments_it_spreads` catches that offline.
- **IOC lookup is one filter item ORing `value` with every `hashes.*` key**, because files have no `value`. OpenCTI matches these case-insensitively. Free-text `search` matches whole tokens only (`sdk.netnut.io` finds that indicator, `netnut` finds nothing), so exact lookups go through filters, not `search`.

Tests: `tests/test_opencti_connector.py` (no DB, no network).

### SOCFortress UBA connector

`app/connectors/uba/` makes CoPilot the analyst UI for [SOCFortress UBA](https://github.com/socfortress/socfortress-uba) (user behavior analytics): a first-party connector named **`SOCFortress UBA`** (`SOCFORTRESS_UBA_URL` / `SOCFORTRESS_UBA_API_KEY`, `api_key` auth), routes under `/api/uba/{customer_code}/…`, and the **Investigate → User Behavior** page (`/uba`, route `Uba`, `components/uba/`).

- **UBA is the store; CoPilot proxies.** Entities ranked by risk, UBA alerts, signals, suppressions, verdicts and native-rule scores live in UBA's Postgres; the routes pass UBA's responses through (`UbaResponse` allows the payload fields; request bodies are typed). UBA's API is documented in its `docs/12-api.md` and at `<UBA URL>/docs`.
- **Tenancy is checked twice.** Every route but `/availability` carries `verify_customer_code_access` (pinned by `tests/test_uba_connector.py`); UBA also scopes its API key to tenants and answers 404 outside them. The UBA tenant *is* the customer code (UBA reads `agent_labels_customer`).
- **A UBA 401/403 is never a CoPilot 401/403** (the frontend would log the analyst out): upstream failures are 502 with a `reason` (`key_rejected`, `insufficient_scope`, `unreachable`, …), 404/422 pass through, a missing or incomplete connector is 409. Same rule as the Customer WAF.
- **The analyst is sent as `X-UBA-Actor`** on writes, so UBA records who suppressed a rule or gave a verdict. Suppressions and verdicts are admin/analyst; native-rule scores (tuning a whole customer's risk) and identity-source test/sync (a customer's directory credentials) are admin only.
- **Directory syncs are configured in UBA, not CoPilot.** The *Directory* tab lists a customer's identity sources (Entra via Graph) with status, last result and error, and can test one or queue a sync (`/identity-sources/{id}/test|sync`). Adding a source and its client secret stays on the UBA host (`uba-admin identity-sources add`): CoPilot's UBA key has write scope, and secrets never pass through CoPilot. The entity drawer shows what UBA knows from the directory: account state, memberships and *why* an identity is privileged.
- **Entity keys travel as `?entity_key=`**, not a path segment: they contain `\`, `:`, `@` (`windows-demo\jdoe`, `upn:jane@contoso.com`).
- **A UBA alert and an entity also have pages** (`/uba/:customerCode/alerts/:alertId`, `/uba/:customerCode/entities/:entityKey`, `components/uba/UbaDetailPage.vue`), the same header and body as the `/uba` drawers, which link them with `ModalPageButton`. The "user behavior" links on a CoPilot incident alert raised by UBA (`AlertUbaLink.vue`) open these pages. In the frontend URL the entity key *is* a path segment: the router encodes it, so it round-trips. The path's prefixes (`/uba/:customerCode`, `…/alerts`, `…/entities`) redirect to `/uba` on that customer and tab, so the path-built breadcrumb never dead-ends.
- **TLS is verified.** UBA's API normally runs over plain HTTP on the private network next to CoPilot (on one Docker host: published on the bridge, `http://172.17.0.1:8010`, since CoPilot's containers have no `host.docker.internal`); behind HTTPS it needs a certificate CoPilot trusts.
- **Two feedback paths, one effect.** UBA alerts also arrive as CoPilot incident alerts (source `uba`, created by UBA through `/api/incidents/alerts/create/manual`); UBA polls their verdicts. A verdict given on the UBA page goes straight to UBA; UBA records it on the incident's delivery so it never applies twice. Since #1239 CoPilot then writes the same verdict onto the linked incident alert (`services/incident_verdict.py`, audited and on the SLA clock), best-effort and reported back as `incident.status` — never overwriting a verdict the incident already has, and never for an unsuppressed false positive while another UBA alert merged into that incident is open (UBA's poller always suppresses, so it would mute rules the analyst chose to keep).
- **UBA reads verdicts in bulk**: `POST /incidents/db_operations/alerts/verdict-state` (admin/analyst, up to 500 ids, verdict fields only) answers for many incident alerts in one query. Visibility is `alert_visibility_filters_for_user`, and an id the caller may not see is listed in `missing` exactly like one that does not exist, so ids cannot be probed across tenants. Since UBA follows verdicts that are *changed or cleared* in CoPilot (socfortress-uba#64), clearing a verdict on a UBA incident alert lifts the suppressions it caused and reopens the UBA alert.

- **Rollback and modes (#1241).** *Learning only* (`PUT /api/uba/{code}/mode`, admin) is a UBA tenant setting: UBA keeps processing and records its alerts, but skips their CoPilot delivery — skipped, not held, so switching back never delivers a backlog (socfortress-uba `feat/tenant-modes`; an older UBA ignores the field, which is reported as `unsupported` rather than trusted). *Rollback* (`GET` preview / `POST` `/api/uba/{code}/rollback`, admin; `services/rollback.py`) removes what setup made, **routing first**: disconnect the UBA ROUTING pipelines from the source streams (from then on nothing reaches the GELF output, so a dead UBA can no longer back Graylog's output buffer up), then the output, pipelines, rules, feed streams, the customer's UBA ALERTS stream, the shared "UBA ALERTS" input only with the last customer's alerts stream, and finally `active: false` in UBA. Deactivating alone does **not** stop UBA processing events that still arrive, which is why Graylog goes first, and why UBA being down never blocks the Graylog side.
  - **Ownership is recorded, not guessed.** Setup records every object it creates or finds in `uba_provisioned_resource` (by Graylog id, `origin` created/found); customers set up before that are taken on by title (`adopted`). Either way an object is only removed if it still looks like setup's (feed stream without stream rules, a routing pipeline running only the customer's `<feed> - …` rules, a rule routing only to the customer's feeds, …) and nothing else uses it (another pipeline, an event definition, another output). Anything else is a *conflict*: reported, never touched. The customer's own streams are a hard guard; the Wazuh rules are never removed (shared; removal needs a manager restart).
  - **Each run is a `uba_rollback` row**: the Graylog snapshot taken before any change, the steps, and checks (each source stream still running with its other pipelines, Graylog's event definitions unchanged, no routing or output to UBA left, tenant inactive). A failed step leaves what depends on it (a pipeline that would not disconnect keeps its feed stream and rules), the run is `partial`, and running it again finishes. Audited as `uba.rollback` / `uba.mode_change`.
  - **Re-enable is setup again.** UBA moves a reactivated tenant's `processed_until` to now, so gap repair never replays the time it was off with alerting on; setup's title lookup never duplicates.
- **The feed output is GELF UDP (#1252), never TCP when UBA can take UDP.** Measured on the lab: with a TCP output, stopping UBA's receiver made Graylog index *nothing* (every stream, every customer) within 40 s, and `output_fault_count_threshold` never engaged — Graylog's output-buffer processors wait on every output a message's streams have, so one blocked output stalls the shared buffer. UDP cannot block. `GET /v1/provisioning`'s `feed_output.protocol` (UBA 1.4.6+) decides; without it (older UBA, TCP-only receiver) setup keeps TCP. Setup compares host, port *and* protocol, so running it again after a UBA upgrade moves an existing output to UDP. What UDP loses, UBA replays from the indexer (reconciliation, gap repair).

Tests: `tests/test_uba_connector.py`, `tests/test_uba_provisioning.py`, `tests/test_uba_rollback.py` (no DB, no network); frontend `components/uba/__tests__/{UbaSetup,UbaRollbackDialog}.spec.ts`.

### SOCFortress WAF per customer (#1165)

A customer can have one or more SOCFortress WAFs (Caddy + Coraza, [waf-platform](https://github.com/socfortress/waf-platform)). CoPilot reads their events, stats and threat intel, and phase 2 will block IPs. `app/customer_waf/`, routes under `/api/customer_waf/{customer_code}[/{waf_id}/…]`, and a **WAF** tab on the customer (phase 3). Phases and design are tracked in #1165.

- **Not an integration or a connector.** One row per WAF in `customer_waf_instances` (hard FK to `customers`, `ON DELETE CASCADE`, unique `(customer_code, name)`). The WAF has no tenant concept, so each row belongs to exactly one customer. Don't move it into `integration_auth_keys` or the `connectors` table.
- **Auth is a WAF service token** (`wafst_…`, from waf-platform#4). The token authenticates *as* a WAF user and carries that user's WAF role: `viewer` means read-only, `admin` can block and manage forwarders, and `operator` can block but can't read sites. `capabilities_for_roles` mirrors the WAF's role table only to *describe* a token in the UI; the WAF enforces its own table. `normalize_token` rejects anything that isn't `wafst_`: a WAF login JWT expires within the hour, and a site API key (`waf_…`) never authenticates to the admin API.
- **The token is write-only and encrypted with its own key.** It is Fernet-encrypted with `WAF_TOKEN_ENCRYPTION_KEY`, with **no fallback**: not the TOTP key, and not derived from `JWT_SECRET`, so rotating either of those can never strand stored WAF tokens. Without the key, saving a WAF is a 400. Nothing returns or logs the plaintext or the ciphertext; the API exposes `token_prefix` only, and a blank token on update keeps the stored one. A rotated key surfaces as `409` "re-enter the token", deliberately not as a WAF auth failure. `tests/test_customer_waf.py` pins that the token appears in no response model and no log line.
- **A WAF id belongs to a tenant.** `services.get_instance_for_customer` is the only way a route turns `{waf_id}` into a row, and it 404s when the row's customer differs from the path's. The path's customer is what `verify_customer_code_access` authorised, so without this check a scoped analyst could reach another tenant's WAF by guessing an id. 404 rather than 403, so ids can't be enumerated.
- **A WAF 401/403 must never become a CoPilot 401/403.** The frontend treats a 401 from our own API as the analyst's session ending and logs them out (`frontend/src/api/session-expiry.ts`). Upstream failures are **502** with a `reason` (`token_rejected`, `insufficient_role`, `unreachable`, `tls_error`, `not_a_waf`, …); a disabled WAF is 409.
- **Always send the WAF timezone-aware timestamps.** The WAF reads a naive `start_time`/`end_time` in its own process's timezone, so the same query matches different windows on different hosts. Found live against a WAF running in MDT, where a naive "last hour" matched nothing. `build_event_params` sends UTC with an explicit offset.
- **`/health` is outside `/api`.** Through the recommended `https://waf-host:8080` URL (the admin UI's nginx, which proxies only `/api/`) it serves the SPA. The connection check therefore relies on `GET /api/v1/users/me` and treats health as optional.
- **IP blocking (#1167) is a custom Coraza rule; the WAF has no blocklist API.** CoPilot creates exactly one shape (`REMOTE_ADDR @ipMatch <target>`, phase 1, deny, `tag:'copilot-block'`) in `services/blocks.py`.
  - **Injection boundary:** the rule text comes only from a parsed `ip_network`. The analyst's reason goes into the WAF rule's *description*, never into the rule text.
  - **Refused:** IPv4 ranges wider than /16 and IPv6 wider than /48.
  - **Idempotent:** no duplicate rule is added for a target that's already blocked, including by the WAF's own Threat Intel rules, which CoPilot lists but **never modifies**.
  - **Unblock disables the rule, never deletes it.** Re-blocking re-enables the same rule.
  - **Judge rules by their text, not the stored `action` field.** Rules created before waf-platform `cbc7b9b` carry a stale `deny` action on what is really a bypass rule.
  - **A block can cite an alert or case only from the WAF's own customer.** That alert gets a `WAF block:` comment.
  - **The WAF sees the address traffic *arrives* from.** Behind a VPN, NAT or proxy that is the shared exit, not the user. Found live: a dev machine on a split tunnel reached the WAF as the VPN's exit address, so blocking its home IP did nothing. Blocking a shared exit blocks everyone behind it; `target_warnings` says so for non-public addresses.
- **TLS to the WAF is not verified by default.** A stock WAF's self-signed admin certificate covers only `127.0.0.1` / `localhost` / `admin-ui`, never its real address, so verification fails against every fresh install. The traffic is still encrypted, but the WAF's identity isn't proven. `verify_tls` (+ optional `ca_cert_pem`) is an opt-in for WAFs with a trusted certificate. Don't flip the default back to on, and don't reintroduce a warning for it: that's the decision, not an oversight. The WAF admin API belongs on a private network or VPN.
- **UI: setup on the customer, use in the menu (#1168).** Customers → customer → **WAF** tab is configuration only (add, edit, test connection, delete); the views live on **Investigate → WAF** (`/waf`, route `Waf`).
  - **URL state:** customer, WAF, tab and an optional `?ip=` pre-filter are in the query. Picker changes `replace`; "Events from this IP" `push`es.
  - **Pickers:** fed by `GET /api/customer_waf`, the one route without a `{customer_code}`. It's scoped with `scoped_customer_codes`, and the `[]` (sees nothing) case short-circuits before the service, which would read `[]` as "all".
  - **Alert IoCs:** "Block at WAF" renders only for an IP IoC whose alert customer has an enabled WAF with a block-capable cached role. The per-customer WAF list is cached in `customerWaf/utils.ts:useCustomerWafs`; invalidate it after config changes.
  - **Chart colour:** the page has one data hue, in `customerWaf/chart-colors.ts`. The theme's light-mode primary is only 2.3:1 on the light surface, so marks use a darker step of it in light mode. Status colours are for pills only.
- **Event forwarding into the SIEM (#1169, `services/forwarding.py`)** creates, per WAF: a Graylog **Syslog TCP input** (no TLS) on a free port in `WAF_SYSLOG_PORT_RANGE`, with two extractors, plus a **syslog forwarder on the WAF**. Per customer, shared by sibling WAFs: the `waf-<code>` index set (daily rotation × 30, 1 shard) and the "SOCFORTRESS WAF - <code>" stream. Every created object's id is recorded on `customer_waf_instances`.
  - **Static fields:** the input adds `syslog_type=waf`, `syslog_customer=<code>` and `waf_name`. The WAF's payload names neither customer nor WAF, and the first two are the exact fields the alert pipeline reads for source and customer. The stream routes on them, not on extracted fields.
  - **The JSON extractor's `waf_` prefix is load-bearing.** Unprefixed, the payload's `timestamp` and `source` overwrite Graylog's own fields: the timestamp fails to parse (`gl2_processing_error`) and the real syslog source is lost.
  - **Inputs, static fields, extractors and index sets** are plain Graylog requests; the stream uses `send_post_request_create_entity`.
  - **Provisioning** prechecks that the WAF token can manage forwarders before touching Graylog, and rolls back newest-first on failure. Reused sibling objects are never undone.
  - **Teardown** removes the forwarder and input, and the stream only with the customer's last forwarding WAF. It **never removes the index set**, so stored events are kept.
  - **The syslog destination (`syslog_host`) is explicit:** it's what the WAF can reach, which is usually not CoPilot's Graylog API URL.
- **Alerts (#1169 4b, `services/alerts.py`)** are two **Monitoring Alerts catalog** entries, provisioned once per Graylog and shared by every customer. The customer comes from each event's `syslog_customer`.
  - **`SOCFORTRESS WAF BLOCKED`** is per-event. `syslog_type:waf AND waf_action:blocked` feeds the existing `gl-events` collector with `COPILOT_ALERT_ID=NONE`. The alert title is `waf_rule_msg`, filled by a third extractor with the first matched rule's message. `create_alert` merges into an open alert with the same title, so repeated blocks for one rule roll up per customer with each IP as an IoC.
  - **`SOCFORTRESS WAF BRUTE FORCE`** is a real threshold: `count() >= 30` grouped by `syslog_customer` + `waf_client_ip`, over 5 min, checked every minute.
  - **Why brute force uses the webhook.** An aggregation event has no `origin_context`, so it can't use the collector. It's delivered by an HTTP notification ("SEND TO COPILOT - WAF THRESHOLD", `api_key_as_header` → `graylog: <GRAYLOG_API_HEADER_VALUE>`) to `/api/incidents/alerts/create/threshold`. That needs `ALERT_FORWARDING_IP` and `GRAYLOG_API_HEADER_VALUE`; without them it's a 400 before anything is created. It must **not** carry `COPILOT_ALERT_ID`, or the collector processes it too.
  - **Titles** must equal `alert_name.replace("_", " ")`; that's how the route's duplicate check finds them.
  - **Pinned to the default Graylog.** `PINNED_TO_DEFAULT_GRAYLOG` in `monitoring_alert/routes/provision.py` makes the route ignore the requested `graylog_instance` for both WAF alerts, because the WAF deployment always ingests on the default connector. A definition on the network Graylog would never see a WAF event.
  - **Both register `waf`** in the incident field-mapping tables idempotently: asset `waf_host`, IoC `waf_client_ip`, title `waf_rule_msg`, time `timestamp`.
  - **Graylog 7 allowlist:** it lives at `/api/system/urlallowlist`. The old `provision_webhook_url_whitelist` helper still PUTs the 6.x path, so don't reuse it on 7.
- **The WAF's event list has no total.** `GET /api/v1/logs/` returns a bare page (`limit` ≤ 500, `offset`), no count in body or headers, and no count endpoint. Counting by probing offsets was measured against a live WAF: 534,592 events took 40 requests and about 3 minutes, with deep offsets up to 10 s each. So the Events tab pages newest first with first / previous / next, asks for one row more than a page to know whether there is a next one, and says "more available" or "last page". Don't bring back a numbered pagination whose page count grows as you go; a real total needs a count from waf-platform first.
- **The Overview's stats get two minutes; every other WAF read gets 15 s (#1261).** `/logs/stats` makes the WAF aggregate its whole log store, and on a WAF with many sites that took longer than 15 s, while the paged Events tab stayed fast. The timeout was also reported as `unreachable`, so the UI blamed the network.
  - **Budgets:** `STATS_TIMEOUT = 120` (`services/customer_waf.py`) applies to that call only. Opening the connection never waits more than `CONNECT_TIMEOUT` (15 s, `utils/universal.py`), so a WAF that is down still reads as unreachable within seconds.
  - **Reasons:** a timeout after connecting is its own reason, `timeout` ("reachable but answered too slowly"); `unreachable` means CoPilot could not connect.
  - **nginx:** the frontend nginx gives `/api/customer_waf/…/stats` a 180 s `proxy_read_timeout`; its 60 s default would answer 504 first. The WAF's own admin nginx already allows 3600 s. `test_nginx_gives_stats_longer_than_the_backend_waits` keeps the two numbers in step. A reverse proxy placed in front of CoPilot needs the same headroom (Cloudflare's proxy gives up at 100 s).
  - **UI:** the Overview says why it is still loading after 8 s and offers *Try again* on an error.
- **Removing a WAF from CoPilot doesn't revoke its token.** A token can't manage tokens, so the delete response tells the operator to revoke it in the WAF UI.

Tests: `tests/test_customer_waf.py` + `tests/test_customer_waf_blocks.py` (no DB, no network). `tests/e2e/customer_waf_e2e.py` uses real routers, real MySQL on 13306 and real JWTs, optionally against a live WAF (`WAF_E2E_URL` / `WAF_E2E_TOKEN`; `WAF_E2E_VERIFY_TLS=true` to opt in to verification). With a block-capable token it also blocks and unblocks TEST-NET addresses only, and deletes the rules afterwards. `tests/e2e/customer_waf_slow_stats_e2e.py` (#1261) runs the whole path a browser takes: the frontend image's nginx template in Docker, the backend over real HTTP and a fake WAF with a chosen delay. It checks the stats and Events budgets and the unreachable cases; `E2E_NGINX_CONF` swaps the nginx template, and 7 of its 14 checks fail against the pre-fix tree.

### Stack provisioning: Graylog content packs and InfluxDB checks

`app/stack_provisioning/` holds two independent provisioners that share a shape (JSON templates on disk + `routes / services / schema`) but nothing else:

- **`graylog/`** — content packs, streams, inputs, pipelines. Templates are Graylog content-pack exports.
- **`influxdb/`** — the four SOCFortress monitoring checks (CPU, memory, disk, critical systemd services). Templates under `influxdb/templates/` are **literal `POST /api/v2/checks` bodies** with two placeholders, `REPLACE_ORG_ID` and `REPLACE_BUCKET`, substituted at provision time.

Things to keep straight in the InfluxDB half:

- **The connector stores the org *name*, the checks API wants the org *ID*.** `connector_extra_data` is `"ORG,BUCKET"` (e.g. `SOCFORTRESS,telegraf`); `get_influxdb_org_id()` resolves name → ID via `GET /api/v2/orgs` on every provision run. Don't pass the name into a check payload — InfluxDB accepts it and then the check belongs to no org.
- **`influxdb_client`'s async client exposes only the query and write APIs.** Checks, notification endpoints and notification rules are not on it, so `app/connectors/influxdb/utils/universal.py` carries plain `httpx` helpers (`send_get_request` / `send_post_request` / `send_put_request` / `send_delete_request`) that authenticate with `Authorization: Token <key>`. Anything touching those three APIs goes through them, not the SDK.
- **Provisioning skips an existing check unless `overwrite=true`.** Stacks are routinely built by hand before CoPilot is pointed at them — `CPU CHECK` in particular usually already exists — and a blind PUT would discard an engineer's tuning. The CPU template is therefore a byte-for-byte copy of the hand-built check so that overwriting it is genuinely a no-op.
- **No new read path is needed and none should be added.** Checks write their results into InfluxDB's `_monitoring` bucket as the `statuses` measurement, which the pre-existing `GET /influxdb/alerts` already queries — so a provisioned check surfaces in the Healthcheck UI automatically.
- **The critical-services check alerts on `failed`, not on "not running", and that is load-bearing.** Telegraf ships inactive units too, and its `active_code` mapping is `active=0, reloading=1, inactive=2, failed=3, activating=4, deactivating=5`. SOCFortress stacks are role-split — `soc-grfna01` runs Grafana, not the indexer — so on any given host most watched units are legitimately stopped (`2`), and units systemd merely carries as `not-found` stubs report `2` as well. A `> 0` threshold therefore CRITs on every service a host doesn't own; the threshold is `> 2` so only a genuinely failed unit alerts. The tradeoff is deliberate: a service stopped by hand and forgotten stays silent. Don't "tighten" this back to `> 0`, and don't assume a unit absent from a host produces no rows — it usually produces `2`.
- **Checks alone notify nobody.** InfluxDB only sends anywhere once notification endpoints + rules exist, and CoPilot provisions neither. Creating checks is safe on a live stack.

### Customer Portal backend conventions (#1188)

- **Global settings have two write verbs.** `POST /customer_portal/settings` replaces the row: a missing or null field restores its default, which is why changing only the title there means re-sending the logo. `PATCH` writes only the fields sent, restores defaults only through `reset: ["title" | "logo" | "brand_color"]`, rejects an explicit null, and takes `logo_base64` and `logo_mime_type` together. The CoPilot editor (`components/customerPortal/Form.vue`) saves with `PATCH`, sending only what changed (`settingsPatch.ts:buildSettingsPatch`); a per-customer override is still one row replaced by `PUT`. Both go through `services/settings.py`; the route commits and then invalidates the branding cache.
- **Branding validation lives once**, in `app/customer_portal/utils/validators.py`, shared by the settings and override schemas; an empty value means unset. Validators raise `ValueError`, so a bad field is the standard 422 naming it (`brand_color: Expected a hex color…`). Never raise `HTTPException` from a schema.
- **Route errors go through `routes/errors.py:internal_errors(action, session)`**: a service's `HTTPException` (403/404) passes through, and anything else is logged with its traceback, rolled back and returned as a generic `Failed to <action>`. Never put `str(e)` in a response: a database error's text carries SQL. `tests/test_customer_portal_route_errors.py` fails on a hand-rolled `except Exception` in a portal route.
- **Timestamps use `app/time_utils.py:now_utc()`**, not the deprecated `datetime.utcnow()`. It is timezone-aware, but the columns are naive `DATETIME`, and the driver stores the same UTC wall-clock time as before.
- `tests/e2e/customer_portal_settings_e2e.py` runs all of this against the disposable 13306 MySQL.

### What a portal user may write: the `customer_user` allowlist

Tenant checks stop a customer from touching *another* tenant's data; what they may do to their *own* SOC record is a separate product decision, pinned by `tests/test_customer_user_write_allowlist.py`. A customer can triage (alert/case status, comments, link/unlink alerts, assignee), open cases, upload case files, generate and delete their own reports, flag critical assets and manage their own password/2FA. **Deleting alerts, cases or case files, escalating, moving a case to another customer, firing the Shuffle case notification and refreshing the deployment-wide rules cache are analyst-only.** The test enumerates every non-GET route whose scope admits `customer_user` and fails on any drift in either direction, so adding `customer_user` to a write route means updating `ALLOWED_CUSTOMER_USER_WRITES` on purpose. Read-only POSTs (panel data, rule lookups, logtest) are listed there too.

**Comments carry authorship only in `user_name`, so the routes own it**: create and edit stamp it from the caller (the body's `user_name` is ignored), a `customer_user` may edit or delete only their own comments (admin/analyst still moderate any), and edit resolves the alert/case from the comment itself rather than the body — otherwise a caller could name their own alert and a comment id from another tenant. `tests/test_comment_authorship.py`.

### Customer Portal query budget (#1181)

Round-trips, not SQL complexity, are what these pages cost (see `app/connectors/cache.py`), so the portal reads are shaped to minimise them:

- **`GET /customer_portal/overview`** (`services/overview.py`) serves the whole Overview in one call, from light projections (`schema/overview.py`), not `AlertOut`/`CaseOut`. Alert visibility is built once and shared by the counts, the recent alerts and the AI findings; agents are counted in SQL. Each section carries its own `error` and a failing section is rolled back, so it never blanks the others — keep that when adding a section. Measured: 52 → 11 statements for a portal user.
- **Per-status counts are one `GROUP BY`**: `alert_status_counts_for_user` / `case_status_counts_for_user` return a `StatusCounts`. Don't reintroduce a count per status.
- **`get_user_accessible_customers` is memoized in `session.info`**, i.e. per request (`get_db` is a cached dependency). A write to `user_customer_access` must call `customer_access_handler.forget_accessible_customers(session, user_id)` after its commit, or the same request keeps reading the old scope.
- **`alert_visibility_filters_for_user` is the only definition of which alerts a user may see** — the portal AI surface adds its switch on top (`with_ai_report_switch`) instead of copying it. It returns `None` for "sees nothing": short-circuit, never run the query.
- **Resolved branding is cached in-process** (`services/branding_cache.py`, `BRANDING_CACHE_TTL_SECONDS`). Every write to `customer_portal_settings` or `customer_portal_branding` must call `branding_cache.invalidate_all()` after its commit (all entries: a global change reaches every customer); `tests/test_branding_cache.py` checks the three routes that write today.
- **`tests/e2e/customer_portal_overview_e2e.py`** runs all of the above against a real MySQL (the disposable 13306 setup in its docstring): Overview = the four calls it replaced, field by field; the seeded counts; a statement budget (`MAX_OVERVIEW_STATEMENTS`) and one `user_customer_access` read; assignment, AI-switch and branding changes seen on the next request. Exits non-zero on failure — run it after touching any of this.
- **Browser level: `customer-portal/cypress/`** (`pnpm test:e2e` from `customer-portal/`, which starts a backend on :5101 and a portal on :3101 against the same 13306 database and seed, `backend/tests/e2e/portal_overview_seed.py`). Selectors are `data-testid` attributes — keep them when restyling those components. Note the analyst frontend's browser tests are Playwright (`frontend/e2e/`); the portal's are Cypress.
- **No index is missing for "latest AI report per alert"**: InnoDB secondary indexes carry the primary key, so `ix_ai_analyst_report_alert_id` already serves `MAX(id) GROUP BY alert_id` as a covering skip scan (EXPLAIN on 50k reports).

### Customer Portal frontend weight (#1185)

- **The code highlighter is `shiki/core` + the JavaScript regex engine** (`customer-portal/src/utils/highlighter.ts`): only the languages listed there are bundled. Importing from `shiki` itself brings back ~200 language chunks and the Oniguruma WebAssembly (the build went from 14 MB / 347 JS files to 5.3 MB / 48). The highlighter starts with **no** language: `loadLanguages` downloads only the grammars a block names (aliases such as `ps1`/`bash`/`yml` resolved by `canonicalLanguage`), and `Markdown.vue` reads them off the report with `fencedLanguages` before rendering — creating it with every grammar made opening any report fetch 26 files. A language that is not listed renders as plain text (`supportedLanguage`, `fallbackLanguage` in `Markdown.vue`) — never let an unknown fenced block throw. `Markdown.vue` is lazy-loaded; keep it out of the entry chunk. Every route, the Overview included, is a `() => import()`.
- **Server-paginated lists go through `composables/common/usePaginatedLoad.ts`**: one watcher, one load per mount or change, back to page 1 when a filter changes. Debounce only typed text (`refDebounced`) — never the load itself, which delayed every click by 400 ms.
- **The agents list is server-side**: `GET /customer_portal/agents` (page, filters, cards over the whole scope, filter options) and `/customer_portal/agents/export` (CSV of every filtered agent, ISO timestamps). `/agents` keeps returning the whole list for its other callers.
- **Alert filter options skip the asset names** in the portal (`include_assets=false`); the asset filter searches `/incidents/db_operations/alerts/filter-options/assets`. Both go through `alert_visibility_filters_for_user` (the options endpoint carried a third copy of the visibility rules).
- **Leaving a page aborts its reads** (`src/api/navigation-abort.ts`, the portal's copy of the analyst frontend's #1072): every GET joins the current route's `AbortSignal`, reset in the router's `beforeEach` on a path change (not a query change), and the backend's `ClientDisconnectMiddleware` stops the handler. Unlike the analyst frontend, a caller's own `signal` does not opt out — portal lists own a controller only to cancel a superseded load — so the request follows both. A navigation-cancelled request never settles (no toast, no update on a page that is gone). Never POST/PUT/DELETE. Mark `keepOnNavigation: true` on anything not page-scoped: branding, token refresh, the cached AI availability (an unsettled promise would sit in its cache), the report poller, downloads.
- **A list's load goes through `composables/common/useLatestRequest.ts` (#1192)**: `run(signal => …, onError)` aborts the load still in flight, clears `loading` in a `finally` for the latest load only, ignores a superseded load's error and cancels on unmount. The lists used to clear `loading` inside `try`/`catch` and skip it on a cancellation, which could leave the spinner on. Don't hand-roll an `AbortController` in a list again.
- **"Filter by key = value" is `components/common/KeyValueFilter.vue`**, used by the alerts and cases lists: the list passes `loadOptions`, and optionally a `searchKey` whose values are searched on the server (`search`) — the alerts' asset names.
- **Asynchronous code is async/await**: `src/utils/__tests__/async-style.spec.ts` fails on any `.then(` in `src/`. Mind handlers passed to naive-ui components that await a returned promise (`n-popconfirm`'s `@positive-click` keeps the popup open until it settles): call an async function there without returning its promise, as `UnlinkCase.vue` does.
- **Customers are shown by name (#1243).** The token carries only codes, and a snapshot of them taken at login; `GET /customer_portal/me` (`customer_user` only, `services/me.py`) returns the caller's customers with names, read live, so an assignment changed after login shows at the next page load. `stores/auth.ts:loadProfile` fetches it at boot and at every login, `accessibleCustomers` falls back to the token's codes until it answers (and when it fails), and `customerName(code)` falls back to the code. Pickers and labels go through `composables/common/useCustomers.ts` (name as label, code as value, found by either, code beside the name) and `components/common/CustomerName.vue`; never print `customer_code` raw. Every form that files something under a customer (case, report, event search) seeds it with `useCustomerPrefill` and re-seeds on every open: the global filter when it resolves to one customer, else the user's only customer, else the user chooses. `customerFilter.pruneToAccessible` replaces the selection only when it drops something — a new array with the same codes would reload every list.
- Watch the customer filter through `customerFilterStore.queryCustomerCodes`, without `deep`: the store replaces the array on every change. Keep it that way — mutating it in place would silently stop every shallow watcher (`cypress/e2e/customer-filter.cy.ts` catches it).
- **Checks, from `customer-portal/`:** `pnpm test:unit` (Vitest, `src/**/__tests__/*.spec.ts`: `usePaginatedLoad`, `useLatestRequest`, `KeyValueFilter`, the highlighter, the Overview mappers, the agents endpoints, navigation-scoped cancellation, the async style), `pnpm check:bundle` (production build must carry only the grammars declared in `utils/highlighter.ts`, no WebAssembly, every routed page except the login as its own lazy chunk, entry chunk within its gzip budget), `pnpm test:e2e` (Cypress, see `cypress/README.md`).

### Customer Portal alerts: combined filters in the URL (#1245)

- **One request for every filter**: the portal's alerts list calls `GET /incidents/db_operations/alerts/filter` (title, status, source, asset, tags = any of them, and `date_from`/`date_to` on `alert_creation_time`, inclusive, an aware time converted with `time_utils.to_naive_utc`; reversed range → 422). - **The page and `total_filtered` share one visibility**: the route builds `alert_visibility_filters_for_user` once and passes it as `visibility` to both `list_alerts_multiple_filters` and `alerts_total_multiple_filters` (the criteria themselves come from `_alert_criteria`). - **Tag-visibility `EXISTS` clauses are `.correlate(Alert)`**: the filtered list joins `AlertToTag` for its tag criterion, and auto-correlation took that table out of the subquery too (`returned no FROM clauses`) — every filtered list of a tag-restricted analyst was a 500.

Dates are local calendar days; the API gets local midnight → last local millisecond as UTC. Tests: `tests/test_alert_combined_filters.py` (no DB), `tests/e2e/alert_filters_e2e.py` (13306: criteria, dates, customer scoping, a tag-restricted analyst), portal `components/alerts/**/__tests__/`, `cypress/e2e/alert-filters.cy.ts`.

### Customer Portal agent details: Vulnerabilities, SCA and Cases (#1256)

`components/agents/AgentDetails/` has four tabs: Overview, Vulnerabilities, SCA and Cases. Each loads only when first opened. They read routes the backend already served to `customer_user` (`app/agents/routes/agents.py`), each checking the agent's tenant (another customer's agent is a 404, and Wazuh is never asked about it). The filtering, counting and ordering are pure functions in `agentFindings.ts`.

- **Vulnerabilities are fetched once with every severity** (`/{agent_id}/vulnerabilities/All`); the severity filter, counts, search and paging are client-side. The CSV export asks for the severity on screen.
- **The CSV's EPSS column is best-effort and batched** (`threat_intel/services/epss.py:collect_epss_scores`, 100 CVEs a request). It used to make one call to api.first.org per CVE, and one failure made the whole export a 500. An unreachable EPSS (an air-gapped deployment) now leaves the column empty.
- **`GET /agents/{hostname}/cases` was a cross-tenant leak.** It checked that the caller sees *an* agent with that hostname, then listed every case with an alert on that asset name across tenants. ### Customer Portal reports: status polling and a Download when ready (#1263)

- **The poller reads the reports it waits for, nothing else.** `stores/reportGeneration.ts` asks `GET /incidents/customer_reports/status?ids=…` (admin/analyst/customer_user, 1–50 ids, `paramsSerializer: { indexes: null }`), one request at a time, every 3 s for the first minute, 10 s up to five, then 30 s (`pollDelay`), and stops when nothing is pending; it used to reload the whole list every 5 s. The route reads six columns in one query; `report_visibility_filters` is the one definition of what the list and the poll may show, so an id the list hides (another customer's, an analyst report not shared with the portal, a deleted one) comes back in `missing`, indistinguishable from one that never existed.

The Reports page counts on its own from `generated_at`, read as UTC (`reportTiming.ts`): "Generating · 3 min". Using a toast's action closes the toast.

- **Generation answers with URLs that exist**: `check_status_url` is the poll, `download_url` the download, both under `/api` (they said `/api/v1`, under which nothing is mounted).
- **`MINIO_URL` takes `host` or `host:port`** (`data_store_session.minio_endpoint`; a bare host still gets `:9000`). The e2e MinIO listens on 19000, like MySQL on 13306.

### Customer Portal event search: saved queries, CSV export and columns (#1258)

`components/eventSearch/` in the portal, and `/api/siem/event_search` in the backend.

- **Saved and recent searches and the picked columns live on the server**, per user and customer, so a user finds them on any device: `event_search_saved_query` (unique on user, customer, name), `event_search_recent_query` and `event_search_columns` (unique on user, customer, source), in `app/siem/models/event_search.py`. Both keys are hard FKs with `ON DELETE CASCADE`; `source_name` is not an FK, so a search saved on a source the SOC later removes stays listed and the portal says the source is gone.

The user comes from the token, never the body; the customer goes through `check_customer_access`; someone else's query id is a 404. Every route answers with the whole memory, which the portal takes as is. The writes are in `ALLOWED_CUSTOMER_USER_WRITES`.
- **Rules are the server's** (`services/event_search.py`, `utils/event_search.py`): a name saved again updates that query, compared with the column's collation (case- and accent-insensitive by default, the same rule as the unique key); at most 50 saved per customer, and the 51st is a 409, never a silent drop; the last ten recent, a search once whatever its page size. Absolute ranges travel as ISO 8601 with an offset and are stored as naive UTC.
- **Every write locks the user's row after a commit.** Under MySQL's REPEATABLE READ a transaction reads the snapshot of its first plain read, and the route has already read (the access check): without the commit, two devices could both take the last slot (`tests/e2e/event_search_e2e.py` section H races them).

An answer older than one already taken is ignored. Recording a recent search never gets in the user's way: a failure is only logged.
- **A saved query is restored only if its source still exists** for that customer; otherwise it says so rather than running. `SearchForm.restore` waits a `nextTick` before searching: `query` is the parent's `v-model`, which reads the new text only once the parent has rendered.
- **The table and the CSV share one column definition** (`eventColumns.ts:resolveColumns`): the user's columns for the source, else the SOC's `displayed_columns`, else the default layout. The export writes the events loaded so far (it says when more are left) with times as ISO 8601 UTC; an offset-less time from the indexer is UTC.
- **The next-page token is bound to its search.** `GET /siem/events/{code}/{source}?scroll_id=` used to hand any scroll id to the indexer: the route checked only the customer in the path, and a scroll id names a search context, not a tenant (it travels in a query string and is built from per-node counters). `query_events` now returns the scroll id signed with the customer and source (`app/siem/utils/scroll_token.py`, HMAC with the JWT secret) and continues only a token issued for that pair, after the source is looked up again (a source disabled since stops there). Anything else is a 400 "run the search again". Clients treat the token as opaque; the analyst frontend is unaffected.

### Customer Portal Overview trend and AI analysis status (#1273)

- **The trend is its own call**: `GET /customer_portal/overview/trend?range=7d|30d` (`services/overview_trend.py`), so the one-call Overview (#1181) stays light. It counts **opened from `opened_at` and closed from `resolved_at`** of `soc_sla_alert_tracking` / `soc_sla_case_tracking` — never `alert_creation_time`, which ingest moves to the latest trigger. A reopened item has no `resolved_at`, so it stops counting as closed. Items from before the SLA tracking tables have no clock and are not in the trend.
- **Per UTC hour, in SQL; days are the viewer's.** One `UNION ALL … GROUP BY` per entity returns hours with something in them, over the range plus one day; the portal sums them into local days (`components/overview/trend/trend.ts:trendDays`, DST-safe: each midnight is read in the timezone from the plain date, since adding days to a zoned dayjs keeps its offset) and lists every day, empty ones included. Don't bucket by day on the server: a UTC day is not the customer's day.
- **Two Nets.** The relative one is opened − closed and can be negative: the closed include items opened before the window. The absolute one is how many are still open: the API also answers `alerts_open_at_since` / `cases_open_at_since` (opened before the window, not resolved before it), and the portal adds each hour's opened − closed to it to get what was open at the end of every local day. "264 opened, 280 closed" means the backlog shrank by 16, never "0 open" nor "264 open". "Still open" means not resolved (open, in progress or waiting on you), so it is larger than the posture card's OPEN count.
- **An item CLOSED without `resolved_at` is left out of every count.** The SLA migration backfilled `resolved_at` from `time_closed`, which some closed items never had; counted opened but never closed, it would keep the absolute Net above zero for ever. No closing time is invented for it.
- **Visibility is the usual pair**: `alert_visibility_filters_for_user` for alerts (tag RBAC included; `None` → no query) and `resolve_effective_customers` for cases (`[]` → no query, and 0 open). Each entity fails on its own (`alerts_error` / `cases_error`, generic text, rolled back, anchor `null`): two statements per entity.
- **Portal**: `OverviewTrendPanel.vue` leads with what is still open now (and at the start), then the period's Net, opened, closed and the peak; the chart (`OverviewTrendChart.vue`) has two bands on one calendar, each with its own scale: still open at the end of each day as a neutral area (peak and today marked), opened up and closed down as bars below. A screen-reader table carries every day. Alerts/Cases and 7d/30d sit in the panel header; the period is `?trend=7d` (`replace`; the default `30d` is left out of the URL). The alerts and cases posture cells carry a sparkline of opened per day. Colours are `TREND_COLORS` (opened/closed validated per mode; still open is a neutral ink, not a third hue). `ChartColumn` was not reused: it is one series with a colour per bar.
- **AI investigation status** (`AlertDetails/aiInvestigation.ts`): one map from status to label and colour ("Queued", "Analysing", "Completed", "Failed"); an active job older than `STALE_INVESTIGATION_MS` (2 h, the backend's own cutoff) reads "Stalled". The elapsed time ("Analysing · 4 min") counts from `started_at ?? created_at`, which are naive UTC: read them with `utcMillis` / `formatDate(…, { tz: true })`, never as local time. `utils/elapsed.ts` (moved from `reports/reportTiming.ts`) formats it for the reports too.

Portal users can be told about their own customer's events, in the portal's bell and by email. CoPilot's notification engine (`app/notifications/`) stays the SOC's: these are not routes.   - In the portal, `useServerNotifications` caches the availability for the session, loads the first page when the toolbar mounts, then polls only the count every 60 s, never while hidden, re-reading the page when the count moves. It is reset at logout.
  - `useBell` shows the server's items when on, else the session list as before. Server items are marked read for good and have no Delete or Clear.
  - A "waiting on you" item carries `accent: "waiting"`, so the bell paints it in the `waiting` colour (#1278); its toast keeps a type naive-ui knows.
  - *Profile → Notifications* exists only while notifications are on: the emails' `?tab=notifications` link, opened once they are off (or the switch turned off with the tab open), shows Settings rather than an empty page.
  - The report poller then only pops its toast (`toastOnly`), since the bell gets "report ready" from the server.

A read failure is a 502 with a fixed text, through `internal_errors` like every portal route.

- **Errors are data, not zeros.** A Wazuh failure is `error` on a 200 with a fixed text; the portal then shows "—" for every count and card, never 0 ("none found"), with a retry.
- **Portal**: severity, search (debounced) and page in the URL (`exposure.ts:withExposureQuery`, `replace`; switching tabs keeps the filters). A CVE opens a drawer (`CveDrawer.vue`) whose agents link to `/agents/:id?tab=vulnerabilities&search=<CVE>`; a policy's agents link to `?tab=sca&policy=<id>` — `AgentDetails` takes `initialTab` / `initialSearch` / `initialPolicy` from the query. Only `http(s)` references are links.

*Customers → customer → Agents → Healthcheck Wazuh / Velociraptor*: the Unhealthy group has checkboxes, a selection bar and **Delete selected**, which opens `components/customers/healthcheck/UnhealthyAgentsDeleteDialog.vue`. The dialog starts from the filter the list was *read* with (30 days when that one is under a day) and offers 24 h / 7 d / 30 d / 90 d or any value; under 7 days it warns, and **every deletion asks for the count to be typed**, two agents at 90 days as much as fifty at one: it cannot be undone (step 3 lists that among the consequences rather than as a red warning, which read as a refusal). The dialog is three numbered steps on a rail (threshold, review, confirm), each marked to do, current or done. The list's own default is one day, and an empty filter there means zero: a threshold for deleting is never inherited silently.
- **Every agent is judged again at the request** (`judge`), never taken from the list the browser read: `deletable`; `seen_recently` (the list's tool saw it within the threshold, *or* its time is in the future: the list calls that unhealthy, a deletion never does); `active_elsewhere` (the other tool still sees it: a live endpoint with one broken agent, kept unless `include_active_elsewhere`); `wazuh_manager` (`000`, never); `not_found` (unknown or another customer's, told apart from nothing: no hostname echoed). The dialog cannot be closed while it runs. After a run the list is read again and the selection starts over.
- The healthcheck compared the columns' naive UTC with a local `datetime.now()`: on a host off UTC every agent looked hours older (or younger). `is_*_agent_unhealthy` now compare in UTC and take a `now`.

### Tenant scoping: customer codes are not the only tenant key

#1050 made `user_customer_access` authoritative for analysts and guarded every route
whose path carried a literal `{customer_code}`. The reporter came straight back with
"analyst with one customer assigned, still able to see other customer information", and
the reason is structural: **most of a tenant's data is not addressed by its customer
code.** It is addressed by an agent id, a hostname, a Velociraptor client id, a report
id, a job id, a dashboard `template_key`, or a customer *name* — none of which the
`{customer_code}` scan could see. Closing the list view while leaving those open is
security theatre.

The primitives live in `app/middleware/customer_access.py` alongside the #1050 ones:

- **`enforce_owned_object_access(user, owner_code, session, subject=…)`** — the base
  decision, taking an owner already resolved from whatever key the route uses. It is
  **fail-closed**: `owner_code=None` (unknown agent, orphaned row, typo'd hostname) is
  denied for a scoped caller. Not being able to prove ownership is not permission.
- **`verify_agent_id_access` / `verify_hostname_access`** — route dependencies for
  `{agent_id}` / `{hostname}` path params, resolving through `agents.customer_code`.
- **`verify_customer_name_access`** — for `{customer_name}`, which
  `custom_alert_creation_settings` is keyed by (the *name* column, not the code).
- **`scoped_customer_codes(user, requested, session)`** — for aggregates whose service
  takes a `customer_codes` filter. Returns `None` (no filtering), `[]` (**caller sees
  nothing — the route must return an empty result itself**) or a concrete list. The `[]`
  case matters: nearly every service reads an empty list as "all customers", so passing
  it straight through leaks the deployment.

Rules when adding a route:

- **The tenant is wherever the caller names it.** A path param gets a dependency; a
  *body* field (`request.customer_code`, `agents_list`, an upload's `Form(...)`) cannot
  be reached by a dependency and must be enforced in the handler — see
  `active_response.invoke_active_response_route`, `file_analysis.submit`/`upload`,
  `ai_analyst.create_job_route`.
- **Objects addressed by their own id still belong to someone.** Every `AiAnalyst*`
  table carries `customer_code` directly; `custom_dashboard_templates.customer_code` is
  nullable and NULL means shared, so only a scoped template is guarded; a file-analysis
  job carries its customer in the MinIO job blob.
- **Wazuh's active response reads an absent/empty `agents_list` as *every agent in the
  deployment*.** `["*"]` from the UI normalises to `[]` before the handler sees it, so a
  scoped caller must name their targets and own each one; the empty case is a 403 rather
  than a silent fan-out across tenants.
- **Admins stay deployment-wide everywhere.** Analysts and responders see exactly the
  customers assigned to them — **no assignment means no customer** (#1219 removed the
  pre-#1050 wildcard for unassigned analysts, which was the one remaining way an
  assigned-looking analyst saw everything).

**Analysts and responders always have a customer** (#1219,
`app/auth/services/customer_assignment.py:validate_assignment`): registering one, changing
a user's role to one (`PUT /auth/users/{id}/role/by-name` takes `customer_codes` for that)
and replacing their assignments all 400 without at least one existing customer, and
assigning customers to an admin is refused rather than silently ignored (the Users menu
offers no *Assign Customer* for an admin). An analyst left without customers from before
the upgrade — or created at first SSO sign-in, which has no customer to give — sees
nothing until an admin assigns some; `GET /auth/me/customers` reports that as
`scope: unassigned` (vs `assigned` / `deployment`) and the sidebar filter says so, and the
Users list flags them "No customers".

**Browser e2e** for this area lives in `frontend/e2e/` (Playwright, `pnpm test:e2e`,
`pnpm test:e2e:headed` to watch it). It drives the real app against a real backend on
purpose — an API mock would happily "prove" a tenancy fix that does not exist, since the
whole point is what the server refuses to send. Two traps it detects and explains rather
than failing cryptically: a `pnpm dev` already running proxies `/api` to whatever
`VITE_API_URL` said when *it* started (use `E2E_PORT=5199`), and on macOS AirPlay
Receiver owns port 5000. Its seed borrows two existing customers when the deployment's
licence caps customer creation at one, and writes the pair it settled on to
`e2e/.tenants.json`. See `frontend/e2e/README.md`.

Tests: `tests/test_object_level_customer_scoping.py` (middleware primitives) and
`tests/e2e/analyst_object_scoping_e2e.py` (real routers, real MySQL, real JWT — the
same disposable-13306 setup as `analyst_scoping_e2e.py`). Run the e2e against the
pre-fix tree and 13 of its checks come back 200: that is the bug, reproduced.

### Responder role (#1219)

A **Responder** (`RoleEnum.responder = 5`) is an analyst who may also *act* on endpoints of
the customers assigned to them. It sits between Analyst and Admin; analysts lost nothing.

- **The token carries `["responder", "analyst"]`** (`auth/utils.py:role_scopes`, from
  `models/users.py:ROLE_EXTENDS`), so every analyst route admits a responder without being
  touched. Only response routes name `"responder"`: Velociraptor **command** and
  **quarantine/unquarantine** (`/api/artifacts/command|quarantine`), every **CoPilot
  Actions** route, and **Sysmon config** read + **deploy** (`/api/sysmon_config/…`).
  Uploading a Sysmon config, deleting data-store artifacts and all user/customer/connector
  administration stay admin-only. `tests/test_responder_role.py` enumerates the exact set
  of routes that admit `responder` and fails on drift in either direction.
- **Every response route checks the target's tenant**, since the target is in the body:
  `enforce_hostname_access` per host (an empty CoPilot Action `agent_names` is a 400, never
  a fan-out), `verify_customer_code_access` for Sysmon. CoPilot Action invokes and Sysmon
  deploys write audit events (`response.copilot_action_invoke`, `response.sysmon_deploy`).
- **Role-keyed tables follow `effective_roles`**: a responder gets the analyst role's
  `role_tag_access` tags, and `SOC_ROLES` / `CUSTOMER_SCOPED_SOC_ROLES` replace the
  hard-coded `(1, 2)` lists (SOC usernames, manual notification recipients, SSO allowlist
  roles). Name a role with `RoleEnum(id).name`, never a local id → name map.
- **Frontend**: `authStore.isRoleGranted` admits a responder wherever an analyst is
  admitted (`utils/auth.ts:ROLE_EXTENDS`); `authStore.canRespond` (admin or responder)
  gates the CoPilot Actions / Sysmon Config menu entries and routes and the Command /
  Quarantine tabs. A responder sees Sysmon configs read-only and can deploy them.
- **The role id is fixed at 5** (migration `c1219a2b3c4d` and `add_roles_if_not_exist`
  insert it with an explicit id; the migration refuses if 5 is taken by another role, and
  its downgrade refuses while a responder exists).

### SOCFortress announcements ("What's new", analyst console)

SOCFortress tells CoPilot users about new products, releases, advisories and events through a JSON feed in the public `socfortress/copilot-announcements` repository (`feed.json` on `main`; its README is the publishing guide). `app/announcements/` (`GET /api/announcements`, admin/analyst, so responders too) and `components/announcements/WhatsNew.vue` in the toolbar. Separate from the version banner (`app/version/`, `VersionUpdateBanner.vue`), on purpose.

- **The backend fetches the feed, never the browser** (`services/announcements.py`): `ANNOUNCEMENTS_FEED_URL` (default the raw GitHub URL), 5 s, at most 512 KB of raw bytes with `Accept-Encoding: identity` (an encoded answer is refused), cached an hour (`ANNOUNCEMENTS_CACHE_TTL_SECONDS`), a failure cached five minutes. Any failure is an empty list, logged: never an error to the console. `ANNOUNCEMENTS_ENABLED=false` makes no request at all (air-gapped); `ANNOUNCEMENTS_HIDE_PROMOTIONS=true` drops the `promotion` category.
- **Each item is validated alone** (`schema/announcements.py:FeedAnnouncement`; unknown fields ignored, a bad item dropped, never the feed): `https` only for `cta.url` and `image_url` (no credentials, whitespace or backslashes), bounded strings, a known category, `expires_at` after `published_at`. The server filters by publish/expiry time, audience (`admin`/`analyst`/`responder`; a responder also gets `analyst` items) and `min_version`/`max_version` against `CURRENT_VERSION`; `AnnouncementOut` carries none of the targeting fields.
- **No table, no migration: read state is the browser's** (`composables/useAnnouncements.ts`): seen ids in localStorage per username (`copilot.announcements.seen.<username>`), pruned to the ids the feed still carries. The sign-in modal shows unseen `popup` items once per browser session (`sessionStorage`) and marks them seen as it opens; opening the drawer marks everything seen. Reset at logout (`stores/auth.ts:setLogout`). Only SOC roles ask.
- **Rendering**: the body through `Markdown` with `no-images` (no raw HTML); the CTA a `target="_blank" rel="noopener noreferrer"` link; the image `referrerpolicy="no-referrer"`, hidden if it fails. Never the Customer Portal.

Tests: `tests/test_announcements.py` (no network: `httpx.MockTransport`). Frontend: `composables/__tests__/useAnnouncements.spec.ts`, `components/announcements/__tests__/WhatsNew.spec.ts`.

### Global customers filter (analyst frontend)

The sidebar multi-select (`app-layouts/VerticalNav/GlobalCustomerFilter.vue`) writes `stores/customer-filter.ts`; **every consumer goes through `composables/useGlobalCustomerFilter.ts`, never the store directly.** Empty selection means "all accessible customers" — the backend intersects requested codes with `user_customer_access`, so a stale code can never widen access. Four entry points, and picking the wrong one is the usual mistake:

- **`applyGlobalCustomerPrefill(field, formObject, opts)`** — *forms only* (case creation, report generation, config editors). Seeds an empty field once when the form opens and then leaves the user alone.
- **`applyGlobalCustomerCodeFilter()`** — a per-view convention, not a shared helper: the mount-time apply for list views. Deliberately **does not overwrite** a filter the user already set or that arrived via query string.
- **`onGlobalCustomerFilterChange(cb)`** — the live path for list views. Here the global filter **wins** over the local one, because changing the sidebar select is an explicit user action. Gated on the per-user `liveSync` preference (localStorage only, no API, toggled in Profile → Settings) — with it off the callback never fires and views keep mount-time-only behavior. Debounced 300ms inside the hook: the multi-select writes the store on every tag add/remove.
- **`getAvailableGlobalCustomerValue(codes, multiple?)`** — when the view's picker is bootstrapped from data rather than `/customers` (AI Analyst surfaces list only customers that have runs), so the global code must be intersected with what's actually selectable.

Three conventions the call sites rely on:

- **Views with a `filters[]` array reuse their own `setFilter()`** rather than hand-rolling an upsert — `setFilter([{ type: "customer_code", value: codes[0] ?? null }])` upserts, deletes on null, and submits. Only `cases/CasesList.vue` can't (it holds a single `{type, value}` object).
- **An emptied global selection clears the local filter** *except* where the view renders nothing without a customer (Events search, SIEM Dashboards browser, AI Analyst feedback) — those keep the current one and carry a one-line comment saying so.
- **Components receiving a `preset` prop never live-sync.** A preset is an embedded list locked to a fixed scope; syncing it would break the embedding.

Only `views/Overview.vue` sits outside this: it has its own opt-in switch that reads the global codes reactively through props and ignores `liveSync`. Deliberate — leave it alone unless unifying all four mechanisms.

### SOC Management & SLA (#1187)

`app/soc_management/` (routes under `/api/soc_management`, admin/analyst only) and the **SOC Management** page (`/soc-management`, route `SocManagement`, `components/socManagement/`): SLA policies, response/resolution times, analyst performance, detection-rule quality, per-customer figures, workload, and a PDF operations report. The module is the clean-architecture split the rest of the backend approximates: `domain/` is pure (policy resolution, lifecycle milestones, SLA evaluation, statistics, periods, and `analytics.py`, which computes every figure from plain facts), `services/` loads facts and composes, `routes/` stays thin.

- **`alert_creation_time` is not an opening time.** Ingest moves it to the latest trigger while an alert stays OPEN (`update_alert_creation_time`), so it reads "last seen". SLA clocks live in their own tables — `soc_sla_alert_tracking` / `soc_sla_case_tracking`, one row per item keyed by its id, `ON DELETE CASCADE` — with an immutable `opened_at`. The migration backfilled a row for every existing item with `tracked=0`: those count in volumes and the backlog but in **no** duration or compliance figure (an invented clock is worse than none).
- **Acknowledged = the first SOC action** (decision on the issue): assignment, status change, comment, verdict, escalation, case link, case severity change, or a SOC user creating the item by hand. Customers (`customer_user`) and automation never acknowledge; a customer closing an item still *resolves* it (`resolved_by` records who, and the dashboard reports those closures apart).
- **Actions are recorded in the incidents *routes*, never in the shared services.** Ingest writes comments signed `admin` (Velociraptor payloads, SOCFortress AI), so authorship cannot tell a person from a pipeline; `create_comment` must stay silent. *Opening* is the opposite: it is hooked in the creation services (`create_alert_in_copilot`, `db_operations.create_alert` / `create_case` / `create_case_from_alert`) so no creation path can skip it. `tests/test_soc_management_incident_hooks.py` pins every route and both halves of that rule — a new alert/case mutation route needs a recorder call and a line there.
- **The recorder (`services/lifecycle.py:SlaLifecycleRecorder`) never raises and uses its own session.** A failure is logged and rolled back in *its* session; rolling back the request's session would expire the ORM objects the route is about to return. Milestones are guarded `UPDATE … WHERE <col> IS NULL` writes (`domain/lifecycle.py:plan_milestones`), so two analysts acting at once can never both be "first".
- **Targets are snapshotted at opening** (customer override → global → built-in default, per entity × severity cell, `domain/policy.py`). A policy save changes what new items are promised; `apply_to_open` re-targets open items, and re-targeting only ever moves clocks **still running** — a clock already met or breached keeps the due time it was judged against. Same rule when a case's severity changes.
- **Case severity**: `incident_management_case.severity`, NULL = follow the most severe linked alert (`case_effective_severity`); `PUT /incidents/db_operations/case/severity` (admin/analyst — it moves SLA targets). Linking/unlinking alerts re-targets a derived case.
- **Compliance = met ÷ (met + breached)**; items still on track are out of both sides, and "no outcome" is `None`/—, never 0%. Headline times are **medians** (one bulk close of old noise moves a mean by days), with mean and p90 alongside. "Past SLA now" counts only clocks still running (`ItemFact.live_state`): a late acknowledgement stays a breach in compliance, but is not something to chase.
- **One snapshot per request.** `GET /dashboard` loads facts once (`services/datasets.py`, window = the period *and* its predecessor, for the deltas) and derives every section from them, so the tabs and the attention list cannot disagree; the PDF report renders the same `Snapshot`. Visibility is `alert_visibility_filters_for_user` (customer scoping **and** tag RBAC) for alerts and `resolve_effective_customers` for cases — never a second definition.
- **Per-analyst figures are the admin's view** (decision on the issue): an analyst gets every aggregate but only their own row in Analysts and in the per-assignee workload (`Viewer.sees_all_analysts`). SLA policies: GET admin/analyst, PUT/DELETE admin only.
- **Customer PDF report**: `include_sla` adds a "Service Level Performance" section (full/executive/analytics layouts, computed by `report.customer_sla_context` — no analyst names). Opt-in, and forced off for `customer_user`. The SOC operations report (`GET /soc_management/report`, `templates/soc_operations_report.html`) extends `incidents/templates/_report_base.html` through its `cover_scope` / `confidential` / `extra_styles` blocks; `customer_report.html_to_pdf_bytes` is the shared wkhtmltopdf step.
- **Business hours are a clock basis, chosen per policy cell.** `domain/calendar.py`: `ContinuousClock` (24/7) and `BusinessCalendar` (weekly windows in an IANA timezone, holidays) both answer `add(start, seconds)` and `elapsed(start, end)` — every due time, at-risk fraction and pause credit goes through those two, never through `timedelta`. Windows are local and converted per day, so DST moves the UTC window, not the local one (`tzdata` is in the backend image for that). Calendars live in `soc_sla_calendar` (`customer_code` NULL = global, hard FK otherwise); `CalendarBook` resolves customer → global → `DEFAULT_CALENDAR` (Mon–Fri 09–17 UTC). `soc_sla_policy.business_hours` is part of the cell, and the tracking row snapshots it at opening like the targets. Built-in cells stay 24/7. Routes: `GET/PUT /soc_management/calendars`, `DELETE /calendars/{code}` (writes admin-only, `apply_to_open` re-targets). Don't format a business-hours countdown in wall-clock time: `ItemSlaPanel` shows the due time instead ("64h left" over a weekend for a 4-working-hour target is wrong).
- **`PENDING_CUSTOMER` pauses the clocks** (a fourth status for alerts *and* cases — the column is a plain string, no migration). Entering it stamps `paused_at` (guarded); *any* later status change resumes (`lifecycle.resumes`), pushing the running clocks back by the pause **measured on their basis** (a weekend wait extends a business-hours target by nothing) and banking `paused_seconds` (wall, subtracted from TTR) and `pause_credit_seconds` (basis, re-applied by every re-target). Closing a waiting item resumes it first. A paused clock reads `paused` — unless it was already late when it stopped. Consequences elsewhere: `StatusCounts.pending_customer` (and every count response), `update_*_status` now clears the closed timestamp on *any* non-CLOSED status (a stale one made reports count a reopened case as closed), and the case→alerts cascade lives in `incidents/services/status_cascade.py` (a waiting case takes its OPEN/IN_PROGRESS alerts with it and brings back only those). **Only the SOC sets it**: a `customer_user` asking for `PENDING_CUSTOMER` gets a 403 (`customer_reply.ensure_customer_may_set_status`, bulk skips the item) — it would only stop the SOC's clock on their own item. **A `customer_user` comment on a waiting alert or case hands it back** (`incidents/services/customer_reply.py`, → IN_PROGRESS, resumes the clocks); an analyst's note does not. Ingest's `open_alert_exists` still merges into OPEN only, like IN_PROGRESS.
- **SLA notifications** (`sla_at_risk`, `sla_breached`): internal-scope triggers (`INTERNAL_TRIGGERS`), emitted by the `notify_sla_transitions` scheduler job (every 2 min, `services/notifier.py`). Once per clock and state, enforced by four write-once stamps on the tracking row (`{ack,resolve}_{at_risk,breached}_notified_at`): the job **claims** with a guarded UPDATE and sends only if it won, so overlapping runs never double-send (the job never re-claims; a transient failure after the claim is retried by the notification outbox, below). Don't lean on the dispatch log for this: `dispatch_event` sends first and only then finds an existing `sent` row for `(route_id, dedupe_key)` — it refuses the *log write*, not the delivery (`tests/e2e/soc_management_e2e.py` section L showed a second dispatch of the same event reaching the webhook). Assignment re-notification (A → B → A) currently relies on that, so changing it is a decision of its own. A breach also stamps the at-risk notice; a breach more than `STALE_AFTER` (24h) old when first seen is stamped silently, so the first run after an upgrade does not flood. Events carry the item's severity (route `min_severity` applies) and assignee (`assignee` recipient mode works), dedupe per clock. Built-in template "SLA — running late".
- **Customer Portal SLA page** — opt-in per customer, the same shape as the AI report switch: `customer_portal_sla_settings` (missing row = off), `GET/PUT /customer_portal/sla/settings/{code}` (PUT admin), `GET /customer_portal/sla/availability`, `GET /customer_portal/sla/overview` (GET-only for portal users). `customer_portal/services/sla.py` narrows the caller's customers to the enabled ones *before* computing, then runs `metrics.compute_snapshot` (the analyst dashboard's own figures) and projects it through `customer_portal/schema/sla.py`, which has no field that can carry a person's name — `tests/test_customer_portal_sla.py` pins both. Operators flip it under *Customers → Customer → SLA*. In the portal it is the **Service Levels** page (`/sla`, `components/sla/`), listed only when `GET /sla/availability` says so (`useSlaAvailability`, cached per customer, reset on logout, the one call with `keepOnNavigation`). `PENDING_CUSTOMER` reads **"Waiting on you"** there (`utils/workflowStatus.ts`) and **a customer cannot set it** — it is the SOC asking them for something, and letting them pick it would only stop the SOC's clock on their own item; the selects show it disabled while an item is in it, and the detail pages carry a "waiting on your reply" banner whose Reply opens the comments (the reply is what hands it back).
- **Frontend**: filters, period (`?period=7d` or `custom&from&to`) and tab live in the URL (`useSocFilters`, all `replace`); `useSocDashboard` aborts a superseded load and keeps the previous render dimmed. Chart hues are `charts/chart-colors.ts` (validated per mode with the dataviz palette checks); status colours are for SLA states only, always with an icon and a word. `ItemSlaPanel.vue` shows an item's clocks on the alert and case pages and hides itself when SLA data is not readable. ## Things that bite

- **Notifications go through the outbox (`notification_outbox`, `app/notifications/services/outbox.py`, migration `d0b7e1a2c3f4`).** `emit(event)` stays synchronous and never raises, but its task now writes the row in its own short transaction and then delivers it at once (`drain_key`); a caller about to commit should instead `queued = await outbox.enqueue(event, session)` and, after its commit, `outbox.kick(event)` if queued else `emit(event)` (the AI report and review write-backs and the case-task assignment do). `enqueue` never autoflushes and returns False on an ordinary failure, but **raises** what has already aborted the caller's transaction (MySQL 1213, 1205 with `innodb_rollback_on_timeout`, a lost connection): call it before flushing, and read anything the event needs *before* `session.add`. The `drain_notification_outbox` job (every minute) claims due rows with a guarded `UPDATE … WHERE status='pending'` (one winner across processes), recovers `processing` rows past the lease, prunes (first sweep per process, then daily, in batches), and isolates each row. **Only failures that can't have delivered are retried**: 429/503 at the start of `dispatchers.py`'s "<Provider> returned …", Teams' 429 text, ConnectError/ConnectTimeout/PoolTimeout/DNS (`is_transient_failure`; keep it in step with those texts); a ReadTimeout, any other 5xx or `Dispatcher exception` is final and logged, since webhooks, Teams and Shuffle don't de-duplicate. Backoff to 8 attempts over ~24 h, then `dead`; a dispatch's budget is 45 s per route still to deliver, capped at 600 s (`dispatch_event(route_budget_seconds=, budget_cap_seconds=)`), and the lease outlasts the cap; the same whole-dispatch error twice in a row is `dead` at once only when neither attempt settled a route and it isn't outage-shaped (`_outage_shaped`: timeouts, `OSError`, `OperationalError`, pool timeouts, lost connections back off instead). A budget cut-off can re-send a request it cancelled in flight (Resend's key covers it). `dispatch_event(on_route_settled=…)` reports each route's real result as it finishes (persisted to `route_outcomes` straight away), `skip_route_ids` keeps a retry off settled routes, and a retry also skips routes the log shows `sent` for the key since the row's `created_at`: **the dispatch log alone does not stop a re-send** (it is written after the provider call). `delivery_id` (the row's random `delivery_uuid`) gives Resend an `Idempotency-Key` of `<dedupe_key>:<route>:<uuid>`, unique across installs (a new emission is a new key, so A → B → A still delivers). `dispatch_event` detaches its matched routes before the loop (one route's rollback used to break the rest with MissingGreenlet) and logs an internal event's customer as `""` (the column is NOT NULL). `queued_key` (unique) holds the dedupe key until the first claim, so a key is queued once and a newer event replaces the queued one; after that the key can be queued again. Done rows are kept 7 days, dead 30; the prune runs as its own task beside the sweep. Tests: `tests/test_notification_outbox.py`, `tests/e2e/notification_outbox_mysql_e2e.py`.
- **The webhook's structured payload and `copilot.notification.v1` are external contracts (`app/notifications/services/payload_v1.py`).** Receivers parse the payload's keys, so the pre-v1 keys (`customer_code` … `text`, and `include_full_report`'s flat `report_id`, `recommended_actions`, `report_markdown`, `report_created_at`, `iocs` with `ioc_value`/`ioc_type`/`vt_verdict`/`vt_score`/`details`) keep their names, values, nulls and order; v1 adds `schema` after `text` and, with `include_full_report`, a nested `ai_report` block (null when there's no report or the route may not have it). v1 is append-only: a removed, renamed or retyped field is v2. The block is loaded at delivery (the event's `context.report_id` for a review, else the alert's newest report), never stored on the outbox row, and only through `ai_report_v1_for_route`, `job_id` null on customer routes. **Every report surface follows `report_permitted_for_route`**: a customer route needs `is_ai_reports_enabled` on every trigger, manual and test sends included (`dispatch_event`'s gate covers only the AI triggers), for the v1 block, the flat fields (`WebhookChannel._report`), the `{{report}}` token and `context.ai_report` (`_report_event_for_route`, which renders a gated route on a copy of the event with `ai_report: None`); off, the payload is the "no report yet" one. Internal routes aren't gated. The report must be the event's customer's, and the flat fields, the block and `context.ai_report` all pick it by `created_at desc, id desc`. Bounded to 32 KB (`MAX_AI_REPORT_V1_BYTES`, measured ASCII-escaped). Shuffle (`include_full_report` on its config too) carries it as the input's last line after `COPILOT_NOTIFICATION_V1_JSON: `, ASCII JSON; templates as `context.ai_report_v1`, rendered on a copy of the event because the block depends on the route's scope. `docs/user/notifications.md` "Payload v1" is the receivers' reference; `tests/test_notification_payload_v1.py` pins both shapes.
- **Don't edit `backend/app/routers/__init__.py` or `backend/app/db/all_models.py`** — auto-managed import aggregators, excluded from pre-commit for that reason.
- **Don't write `scheduled_job_metadata.last_success` from inside a job.** It is stamped centrally by `scheduler_listener` on APScheduler's `EVENT_JOB_EXECUTED`, which fires only when the callable returned — a job that raises gets `EVENT_JOB_ERROR` and no stamp, and a job that deliberately no-ops ("cache still fresh, skipping") returns normally and correctly counts as a success. It used to be each job's own job, copy-pasted, and five jobs shipped without it: the four #1072 cache/sidebar refreshers and `prune_audit_log` ran fine for months while the UI reported `last_success: null` (#1135). The per-job writes that predate this still exist and are harmless duplicates — don't add new ones. Note the listener is synchronous and runs in the scheduler's event loop, so the write is handed off as a task; keep a strong reference to it (`_pending_metadata_writes`) or asyncio may collect it mid-await.
- **`Security(get_current_user, scopes=[...])` requires *every* scope listed; "any of these roles" is `require_any_scope(...)`.** FastAPI also adds the scopes of the dependencies above it, and a token carries one role's scopes, so `scopes=["admin", "analyst"]` makes a route nobody can call — `POST /healthcheck/logs` sat dead like that until it was found (and it had no tenant check either, now `enforce_hostname_access`). `tests/test_route_scope_semantics.py` walks every route of the real app and fails if any `get_current_user` would be resolved with more than one scope.
- **The password policy is defined once per app and checked against shared cases (#1265).** Every password a user chooses (create, admin reset, self-service change) goes through `backend/app/auth/schema/password_policy.py`; `frontend/` and `customer-portal/` carry the same rules in an identical `src/utils/password-policy.ts`, used by every form that sets a password. The rules: no Cc/Cf/Cs character, at least 8 characters, at most 72 **bytes** of UTF-8 (bcrypt), a lowercase letter, an uppercase letter, a digit and a symbol (any Unicode punctuation or symbol); any other character is allowed. The portal's reset used to allow only letters, digits and `@$!%*?&#`, refusing passwords that met every rule its message listed. Don't add a regex in a form or a schema: change the three places together, and the cases in `backend/tests/fixtures/password_policy_cases.json` (copied under each app's `src/utils/__tests__/fixtures/`; `tests/test_password_policy.py` fails when the copies or the two TS modules differ). Login never checks the policy, so older passwords keep working.
- **A new router takes two edits**: the file in `app/routers/`, plus the import + `api_router.include_router(...)` in `backend/copilot.py`. Miss the second and the route silently doesn't exist.
- **Alembic autogenerate's model registry is `backend/alembic/env.py`, not `app/db/all_models.py`** — `all_models.py` has many imports commented out and is *not* what env.py loads (env.py imports models directly). **Adding a model to an existing model file is fine** (Python imports the whole module, registering every SQLModel in it). **Adding a model in a brand-new file requires an explicit import in `env.py`** — otherwise the file is never loaded and autogenerate silently skips it.
- **`incident_management_*.customer_code` is a STRING, not a foreign key.** Same for `customer_integrations`, `customer_network_connectors`, `monitoring_alerts`, `custom_alert_creation_settings`. Renaming or deleting a customer does *not* cascade. Don't write joins that assume referential integrity on these columns.
- **AsyncSession + `back_populates` = `MissingGreenlet`** in some cases. `CustomerNotificationRoute` and `NotificationDispatchLog` deliberately omit `back_populates` on their reverse relationships (with code comments explaining why) — bidirectional relationships fire implicit synchronous loads on `flush()` that fail under `AsyncSession`. When adding relationships in async-write paths, prefer one-way FKs and explicit `session.get(...)` over `back_populates`.
- **Reads of the `connectors` table are cached in-process; every write to it must invalidate.** `get_connector_info_from_db` (`app/connectors/utils.py`) is the single funnel for connector credentials — 89 call sites — and it now reads through `app/connectors/cache.py` (10-min TTL, `CONNECTOR_CACHE_TTL_SECONDS=0` disables it). Connector rows are deployment-wide and change only on operator action, which is what makes this safe; what makes it *correct* is that `ConnectorServices.update_connector_by_id` / `verify_connector_by_id` / `save_file` each call `connector_cache.invalidate(name)` **after** their `await session.commit()`. A new write path that skips it leaves outbound calls using a rotated credential's predecessor for up to the TTL; invalidating *before* the commit is just as wrong, because a concurrent read re-caches the pre-commit row. `tests/test_connector_cache.py` pins both. Note also that `Connectors.history_logs` is `lazy="selectin"` and is read nowhere in the codebase, so every uncached `select(Connectors)` costs two statements, not one.
- **`.env` is shared across compose services.** Backend and `copilot-mcp` both read it; many MCP vars fall back to `WAZUH_*` defaults — renaming without fixing fallbacks breaks MCP wiring.
- **Black line length is 140**, not 88. **isort `force_single_line = true`** — combined imports get split.
- **Pydantic 2 strictness regressions are still surfacing across the codebase.** The repo migrated from v1 to v2; v1 was lenient where v2 errors. Five patterns to watch for:
  - **Leading-underscore field annotations get silently dropped as `PrivateAttr`.** A field like `_source: GenericSourceModel` parses as nothing — Pydantic 2 never populates it. Use `source: GenericSourceModel = Field(alias="_source")` plus `model_config = ConfigDict(populate_by_name=True)`. We've hit this on `_source` (`GenericAlertModel`) and `_client_config` (Velociraptor `Organization`).
  - **Pydantic schemas fed SQLAlchemy/SQLModel rows need `model_config = ConfigDict(from_attributes=True)`** (the rename of v1's `orm_mode`). Symptom is a 400/500 with `Input should be a valid dictionary or instance of <ClassName>` even though the input *is* an instance — Pydantic 2 enforces exact class match, and ORM-row → Pydantic-schema extraction requires this config explicitly. Audit signal: any Pydantic class that shares a name with a `SQLModel(table=True)` is suspicious. Whole chains of nested response models (`CustomerIntegrations` → `IntegrationSubscription` → `IntegrationService` → `IntegrationAuthKeys`) need it on every level when joinedload feeds them.
  - **v2 stops coercing `bool→str`, `int→str`, etc.** A schema typed `success: str` whose callers all pass `success=True` worked in v1 (silently coerced to `"True"`); v2 errors with `Input should be a valid string [type=string_type, input_value=True, input_type=bool]`. Fix the schema's type to match what callers actually pass, not the other way around.
  - **A `mode="before"` validator must not leave a model instance in a `Dict[str, Any]` field.** v1 accepted the instance and coerced it; v2 rejects it outright with `Input should be a valid dictionary`. The idiom is to build the per-variant model to *validate*, then put `.model_dump(mode="json")` back into the field — `InvokeActiveResponseRequest.create_alert` (#960) is the worked example, and it dead-lettered the whole Active Response invoke endpoint until someone read the 422 body.
  - **A bare `field: str = None` rejects an explicitly-passed `None`.** The default only applies when the key is *absent*, so `Model(field=None)` raises where `Model()` succeeds — v1 allowed both. This bites hardest on optional fields a caller fills in conditionally (`ValidationErrorItem.message`). Annotate `Optional[str]`.
- **Don't reuse a request schema as a response model.** A create/update schema states what a new row must satisfy; a response has to show what a stored row holds. `GET /customers` validated every row against `CustomerRequestBody` (contact names required, though the columns are nullable), and `GET /auth/users` validated every stored address as `EmailStr`, which rejects reserved domains such as `.local`. One row the UI could never create (manual SQL, an import, an older version) failed the whole list with a 400. Responses now use `CustomerOut` / `CustomerMetaOut` (nullable where the table is) and a plain `str` email; convert with `Model.model_validate(obj)`, since Pydantic 2 rejects an instance of a different model. `tests/test_list_responses_tolerate_stored_data.py` and `tests/e2e/list_responses_e2e.py`.
- **`regex=` → `pattern=` is FastAPI-only.** FastAPI 0.116 deprecated `regex=` on `Query/Path/Header/Body` in favor of `pattern=`. **`sqlmodel.Field` still uses `regex=` and rejects `pattern=`** — blindly running a global rename will crashloop the backend at import time with `TypeError: Field() got an unexpected keyword argument 'pattern'`. Pydantic v2 native `Field` uses `pattern=`. Three different surfaces, three different rules; check the import before renaming.
- **`pyvelociraptor` is pure gRPC transport.** It `json.loads` whatever the Velociraptor server emits in `Response` chunks; it does no semantic deserialization. The shape is whatever the server version picks, and *can change between minor versions*. 0.75.6 changed `_client_config` from a structured object to a YAML string. Schemas for VQL outputs should default to tolerant — drop unused fields, structure only what we actually read, lean on `extra='ignore'`.
- **`elasticsearch7.exceptions.RequestError` message lives on `.info`, not `str(err)`.** `str(err)` returns only the error code (`search_phase_execution_exception`); the human-readable cause is on `err.info`. `_is_text_field_agg_error` in `app/siem/services/dashboards.py` is the canonical example — match against `err.error` for the type and `str(err.info)` for the message.
- **FastAPI route ordering inside a single router: static paths must come before wildcards.** A `@router.get("/{id}")` declared above `@router.get("/library")` will swallow `/library` and try to parse `"library"` as the `id` param, returning a 422 with `Input is not a valid integer`. We've hit this on both the Case Templates Library (`/library` vs `/{template_id}`) and the Detection Catalog (`/catalog/stats`, `/catalog/stories` vs `/catalog/stories/{story_name:path}`). When appending new routes to an existing router, scan for wildcard routes already declared and insert above them.
- **Vue JSX (`<script setup lang="tsx">`) does not use the `:` v-bind prefix.** Inside a `.vue` `<template>` you write `<NTag :bordered="false">`; inside a JSX `render: row => (...)` you write `<NTag bordered={false}>`. Mixing them up — easy when copying from one to the other — produces a Vite parser error (`Unexpected token`). The catalog's `StoriesIndex.vue` / `StoryDetail.vue` are pure-JSX render columns; the surrounding `<template>` is Vue syntax. Don't conflate.
- **SPA sub-views driven by URL query params: `push` to open, `replace` to close.** When a parent component swaps between an index view and a detail view based on a query param (`?story=Foo`), entering the detail must use `router.push` so the browser-back button lands on the index, not on whatever was open before this page. Exiting via an in-app button should use `router.replace` to avoid piling up duplicate index entries in history. Detection Catalog's `DetectionCatalogShell.vue` `openStory` / `closeStory` is the canonical pair — getting this wrong is invisible until a user complains that browser-back skips the index entirely.
- **Iconify icon collections loaded in the frontend: `carbon:`, `mdi:`, `logos:`.** `simple-icons:` and other unbundled sets render as an empty box with no console error. If you reach for `simple-icons:wazuh` or similar, either switch to a loaded set or fall back to a plain text label.
- **`app/connectors/wazuh_manager/utils/universal.py:send_put_request` form-encodes dicts even with `Content-Type: application/json`.** The helper sets the JSON content-type header but then calls `requests.put(data=<dict>)`, which `requests` URL-form-encodes (`key=value&key=value`). Wazuh sees the JSON header but a form-encoded body, tries to parse it as JSON, and 400s with `Expecting value: line 1 column 1 (char 0)`. **Fix at the call site by pre-serializing**: `send_put_request(endpoint="/logtest", data=json.dumps(payload))` — `requests` sends string bodies as-is, no encoding. The wazuh-manager `logtest.py` connector has the canonical example. Don't try to "fix" it by passing a dict and assuming JSON encoding; the helper is used by the rule-file-upload flow which expects raw bytes/XML, and changing it globally would break that path. (Cleaner long-term fix would be a `json_data=True` flag on the helper, but it touches every Wazuh integration that PUTs.)
- **Cross-branch local-DB alembic divergence is invisible until startup.** If you run a migration from a feature branch against your local DB and then switch to a different branch that lacks the migration file, `apply_migrations()` at startup crashes with `Can't locate revision identified by <hash>` — the DB's `alembic_version` table records the missing revision, alembic has no file to walk. **Safe recovery**: `git checkout <other-branch-commit> -- backend/alembic/versions/<missing-revision>_*.py` (plus any predecessors in the chain). That brings the migration *file* into the working tree without changing the DB — the schema the file describes is already applied, alembic just needs the file to recognize the state. Don't `UPDATE alembic_version` manually unless you're prepared to fight it later; don't `alembic downgrade` unless you genuinely want to drop the columns.
- **Don't assume Wazuh alerts live only in `wazuh-alerts-*`.** Real SOCFortress deployments spread alerts across vendor- and customer-prefixed indices: `office365-<customer_code>`, `crowdstrike-<customer_code>`, `carbonblack-<customer_code>`, `huntress_<customer_code>`, ad-hoc `newest-*` test indices, and so on — easily 1500+ on lab clusters. A query targeting only `wazuh-alerts-*` will miss the bulk of real traffic. Equally, `wazuh-*` is *too broad* and includes Wazuh's own internal indices (`wazuh-monitoring-*`, `wazuh-statistics-*`, `wazuh-states-*`, `wazuh-vulnerabilities-*`) — those carry `rule.id` for system/control events with Wazuh's parent-template rule IDs (2 = firewall template, 3 = ids template, 4 = web-log template) that never fire on real analyst alerts but produce massive fake hit counts. **Use ES's native wildcard+exclusion pattern**, not client-side index enumeration: `*,-.*,-_*,-wazuh-monitoring-*,-wazuh-statistics-*,-wazuh-states-*,-wazuh-vulnerabilities-*,-security-auditlog-*` passes as one short string and ES resolves it server-side. `wazuh_firing_stats_cache.py:ALERT_INDEX_PATTERN` is the canonical implementation. Integer coercion on the bucket keys naturally drops vendor-native rule IDs that aren't Wazuh-compatible, so over-including is safe.
- **Don't pass a long index list directly to `client.search(index=[...])`.** The elasticsearch7 client serializes the list as a comma-joined URL path segment. At ~1500 indices that crosses the 4096-byte HTTP line limit and you get `too_long_http_line_exception` from the server. The fix is server-side pattern resolution — pass a short string like `*,-foo-*,-bar-*` to `client.search(index=pattern)` and let ES expand it. Combine with `ignore_unavailable=True, allow_no_indices=True` so per-index permission errors and empty matches don't fail the whole call.
- **Graylog 7.0 wraps entity-creation POSTs in a `CreateEntityRequest` — CoPilot must support both 6.x and 7.x.** SOCFortress still has clients on Graylog 6. In 7.0 the create-entity endpoints changed their request body from a flat object (`{"title": ..., ...}`) to `{"entity": {...}, "share_request": null}`; **neither version accepts the other's shape**, and 7.0 *strictly rejects* unknown properties, so you cannot just always-send the wrapper. The symptom on a flat body against 7.x is a 400 `RequestError` with `"entity cannot be null"` and `reference_path: org.graylog.security.shares.CreateEntityRequest`. **Use `app/connectors/graylog/utils/universal.py:send_post_request_create_entity(endpoint, entity=...)` for any entity-creation POST** — it probes `GET /api/system` for the server's major version (cached 5 min, defaults to 6 on failure so 6.x stays byte-for-byte unchanged) and wraps only when major ≥ 7. **Exactly four endpoints CoPilot uses are wrapped** (verified against the live 7.1.2 server's OpenAPI spec): `POST /api/streams`, `POST /api/events/definitions`, `POST /api/events/notifications`, and content-pack *install* (`POST /api/system/content_packs/{id}/{rev}/installations`). **Everything else is FLAT and must keep using plain `send_post_request`** — `POST /api/system/indices/index_sets` (index-set create), content-pack *upload* (`POST /api/system/content_packs`), all `/api/system/pipelines/*` (rule, pipeline, connections/to_stream), and `/api/events/search`. **No PUT endpoint is wrapped** (`UpdateStreamRequest`, `IndexSetUpdateRequest`, `PipelineSource` are all flat), so don't touch PUTs. Wrapping a flat endpoint breaks it under 7.x's strict-property rejection just as surely as not-wrapping a wrapped one — the four-vs-rest split is load-bearing, not cosmetic. Separately, **7.0 dropped `GET /api/system/urlwhitelist` entirely** (404, not aliased) in favor of `GET /api/system/urlallowlist`; `collector.py:get_url_whitelist_entries` tries the 7.x path first and falls back to the legacy path for 6.x.
- **`notification_template` is not only for notifications — it is also the temporary-password email store, and `temp_password_issued` is a template scope that is NOT a route trigger.** #999 gave operators customisable HTML/subject for the admin-issued temporary-password email by reusing that table (the model comment on `NotificationTemplate.trigger` names this as the reason the column is nullable and free-form) rather than adding a parallel one. There is **no migration and no new table** for this feature. Consequences: (a) `NotificationTrigger.TEMP_PASSWORD_ISSUED` is deliberately excluded from `DISPATCH_TRIGGERS` and rejected by `NotificationRouteCreate`/`Update` — nothing emits it into `dispatch()`, so a route bound to it would be config that silently never fires; (b) the sender is `app/auth/services/temp_password_email.py` over SMTP, synchronous, triggered by an admin pressing Send, **not** a channel provider; (c) its template variables (`user_name`, `temp_password`, `login_url`, `customer_name`, …) are `extra_context` top-level names, not `NotificationEvent` fields, so any test that renders *every* built-in against an alert-shaped event must filter to `DISPATCH_TRIGGERS` first or it will fail under `StrictUndefined`; (d) template selection is **resolution by scope, not stored state** — customer-scoped → shared → seeded built-in → the unchanged pre-#999 plaintext, with a per-send override in the Security tab dialog. Unlike `list_templates`, this path requires an **exact** trigger match: a NULL-trigger template is "usable anywhere" for routes but must never be offered as somebody's password email. Render happens **before** the password is rotated, so a broken template costs a 400 rather than locking the user out, and previews always render `PREVIEW_PASSWORD` — never a real credential.

## File Analysis module (branch 974 — in development)

A two-tier file analysis feature on branch `974-in-console-file-analysis-...`: **Tier 1 static inspection always; Tier 2 detonation pluggable and OFF by default** (`SANDBOX_BACKEND=none|local_vm|remote`). This section is the single source of truth — the old `design/file-analysis/` package (docs + prompts) was removed once the feature was built; everything load-bearing from it is folded in below.

Non-negotiables:

1. **The inspector parses, never executes.** No PSDecode/box-ps in the image — deobfuscation is a pure static transform chain.
2. **CoPilot never touches the Docker API** — only the `inspector-runner` sidecar spawns inspector containers, through an allowlisting socket proxy. One fresh container per job, destroyed after.
3. **Isolation is a merge gate** for anything touching the inspector — `inspector/verify_isolation.ps1` must pass 7/7 (no network, read-only root, non-root user, no caps, container removed after, proxy denies `POST /build`, LibreOffice macros truly off).
4. **Customer file bytes never leave the host by default** — reputation is hash lookup only; uploading a sample to VirusTotal *publishes* it, so it's gated behind `ENRICHMENT_SUBMIT_FILES`.
5. **Multi-tenant always** — `customer_code` is required on submit and stamped on every job, result, and MinIO path.
6. **Cache by SHA256** — inspect once, view forever (see `ENGINE_VERSION` below).

CoPilot conventions this module follows: feature module at `backend/app/file_analysis/` with the standard `routes / services / schema` split; thin top-level router in `app/routers/file_analysis.py` **plus** the second edit in `copilot.py` (`from app.routers import file_analysis` + `api_router.include_router(file_analysis.router)`) — miss the second and the route silently doesn't exist; reuse the existing **Velociraptor** and **VirusTotal** connectors and the `app/threat_intel/` services rather than duplicating either. Auth: `Security(AuthHandler().require_any_scope("admin","analyst"))`. Style gates: black line-length **140**, isort **force_single_line**.

### Verdict policy — why a high malscore alone is NOT malicious

Found during testing: a **benign** `whoami; hostname; Get-Process` script came back **malscore 10.0 / "Malicious"** while VirusTotal said **0/74**. The stored evidence was `family: ''`, no config-extracted C2, and 17 signatures whose max severity was **3** (`mountpoint_manager_access`, `enumerates_physical_drives`, `queries_keyboard_layout`…). CAPE derives malscore by **summing signature hits**, and a freshly-booted Windows guest fires a dozen environmental signatures — plus CAPE's own instrumentation — before the sample does anything. Score-only logic therefore calls clean files malicious, which is not shippable in a SOC tool.

`services/verdict.py` now requires **concrete corroboration** for a malicious dynamic verdict:
- a decoded malware **family/config**, or
- a **C2 endpoint from that config**, or
- a signature at **severity >= `HIGH_SEVERITY_SIGNATURE` (4)** — CAPE's environmental noise tops out at 3.

An uncorroborated high score still raises the verdict to **suspicious** (nothing is hidden — the score and every signature stay visible). `cape.summarize()` derives `summary.verdict` from the *same* function, so the Detonation tab can never disagree with the headline verdict. Trade-off accepted: real malware with no CAPE config extractor and only sev<=3 signatures lands as *suspicious* rather than *malicious*. Environment-side signature tuning on the CAPE box is a separate, later task.

**`verdict_reason`** (new field on `AnalysisResult`, rendered under the verdict on the Overview card) states what actually drove it and deliberately surfaces tier **disagreement**, e.g. *"sandbox: malscore 10 from signature hits only (no malware config, no C2, nothing above severity 3); VirusTotal 0/74 — no engine flagged it"*.

Two real bugs fixed at the same time (both found by reading the stored result, not the report):
1. **Every process had `pid: null`** — CAPE names it **`process_id`** / `parent_id`; `summarize()` read `pid`/`ppid`. This blanked the pid in the UI *and* silently collapsed the process tree (the parent map was keyed on `undefined`, so every process became a root). Also fixed a precedence bug in the same expression where the `if isinstance(...)` ternary bound to the whole `or` chain.
2. **Observed traffic was being labelled C2** — `summarize()` appended *every* contacted host to `c2_ips` and *every* observed domain to `c2_domains`, so Microsoft telemetry showed up as command-and-control (and would have falsely satisfied the new "C2 ⇒ malicious" rule). Observed endpoints now live in `hosts` / **`domains`**; `c2_ips`/`c2_domains` are **config-extracted only**, and the Network tab shows genuine C2 in its own red callout. `ENGINE_VERSION = 7` so previously-cached results re-analyze.

### Tier-1 ATT&CK static behaviour detection (script threats) — NEW

**Gap found by testing** (safe benign-intent samples): a script that runs `vssadmin delete shadows` + `bcdedit … recoveryenabled No` (classic ransomware, T1490) and one that runs `Set-MpPreference -DisableRealtimeMonitoring` + `netsh advfirewall … off` (T1562) both came back **clean** from BOTH tiers. Tier-1 only looked at obfuscation + IOCs (not command/behaviour semantics); Tier-2 CAPE **missed the runtime** because its monitor **failed to inject into the short-lived `cmd`/`vssadmin` children** (`debug.log`: "Monitor injection attempted but failed for process N" — only powershell.exe was monitored). So child-process malicious behaviour is invisible to detonation on the cold-boot guest — a real sandbox limitation, and exactly why static content detection must stand on its own.

**Fix — `inspector/analyzers/behaviors.py`:** a data-driven table of **31 high-precision, ATT&CK-mapped regex rules**, exposed via `behaviors.apply(result, *texts)` and run by **every analyzer with a command surface** — `script.py` (raw + each deobfuscated layer, so an `-enc` payload that unwinds to `vssadmin delete shadows` is still caught), `office.py` (VBA macro source + its decoded layers), `lnk.py` (target+args + decoded), `html.py` (HTA/HTML `<script>` bodies + decoded). Two severities: `malicious` (one hit convicts — shadow-copy/backup deletion T1490, credential dumping T1003/T1003.001, shellcode-injection primitives T1055) and `suspicious` (disable AV/firewall/SmartScreen T1562, download-and-exec T1059.001/T1105, WSH/macro exec T1059.005, decode-staging T1140, account creation/priv T1136/T1098, remote/WMI exec T1021.002/T1047, Run-key/schtasks/service persistence T1547/T1053/T1543, UAC bypass T1548, LOLBin proxy-exec T1218, AMSI bypass, log clearing T1070.001). Matches land in `content["behaviors"]` (`{attack_id, technique, severity, evidence}`) and raise `FLAG_MALICIOUS_BEHAVIOR`/`FLAG_SUSPICIOUS_BEHAVIOR`; `analyzers/verdict.py` escalates (malicious flag → malicious row, suspicious flag → suspicious row) for ALL file types automatically. Inspector `ENGINE_VERSION` → 3; CoPilot `state_store.ENGINE_VERSION` → 11 so already-seen files re-analyze. Validated on a 24-sample battery through the live inspector (4 malicious-tier, 14 suspicious-tier across techniques, 6 benign guards) → **24/24, zero false positives**, plus end-to-end through the real orchestrator (`ransom_sim.ps1` → malicious with T1490 ×3 + evidence) and 17 unit cases in `inspector/tests/test_behaviors.py`. This is the resilient detection path: TTPs are caught statically across delivery vectors (scripts, macros, LNK, HTA) regardless of whether detonation captured runtime behaviour.

**Tier-1 inspector must be running** for any of this (and to avoid a false-positive class): when the inspector service (`INSPECTOR_URL`, default `:9100`) is unreachable, every file fails **closed** to `analysis_incomplete → verdict_hint: suspicious` (`inspector_client.py:51`) — that is how a benign photo showed "suspicious" (root cause: the inspector was down). `explain_verdict()` now takes the inspector dict and, on `analysis_incomplete`, states *"Tier-1 static inspection incomplete (<error>) — provisional fail-closed verdict, not a content-based finding"* instead of a bare "static inspection: suspicious" that reads like a content judgement. **Dev without Docker:** run the inspector on the host — `cd inspector-runner && INSPECTOR_MODE=service FILE_ANALYSIS_DEV_MODE=true INSPECTOR_SRC=<repo>/inspector <venv>/python -m uvicorn main:app --port 9100` (needs `oletools pefile LnkParse3 extract-msg py7zr` in the venv; `python-magic`'s libmagic DB is thin on Windows so `filetype` may read `unknown`, but production's containerised inspector has full libmagic).

### Verdict calibration — low-confidence static-PE / .NET-JIT signatures (NEW)

A second false-positive class, found by detonating benign real binaries: **packed/signed native EXEs and .NET assemblies read *suspicious*/*malicious*** even though their runtime behaviour is clean. Measured: RealVNC's `vncviewer64` (malscore 1.5, 5 sigs) and Windows `powershell.exe` (malscore 2.5, 4 sigs) trip only **static PE-structure heuristics** (`pe_cert_self_signed`, `pe_tls_callbacks`, `packer_unknown_pe_section_name`, `contains_pe_overlay`, `pe_compile_timestomping`, `static_pe_pdbpath`, `packer_entropy`); the `Deceive` .NET tool (malscore **8**) trips a wall of **`unbacked_*`** signatures because the **CLR JIT-compiles managed code into dynamically-allocated (unbacked) memory** — indistinguishable from shellcode to CAPE's heuristics, and present on *every* .NET binary. Fix in `services/verdict.py`: a **`LOW_CONFIDENCE_SIGNATURES`** frozenset (the static-PE set + all `unbacked_*` + `injection_rwx`/`network_bind` + weak `antidebug_guardpages`/`query_fips_reconnaissance`). `meaningful_signatures()` now excludes BOTH noise and low-confidence; `noise_stats()` gains a `low_confidence` count; `explain_verdict()` says *"malscore N is static packer / .NET-JIT heuristics only (X/Y fire on benign software)"*; `cape.summarize()` tags each signature `low_confidence`; DetonationTab shows them in their own collapsed "not counted toward the verdict" group. **Validated on the real reports:** vncviewer 1.5 → **clean**, Deceive 8 → **suspicious** (was malicious — the remaining meaningful signal is HTTP + a YARA/packer hit, which legitimately warrants a look), while a run with a genuine behavioural signature (e.g. `modifies_boot_config`) still reads suspicious and config/C2/high-sev still reads malicious. Tests in `test_verdict.py` (5 new). `state_store.ENGINE_VERSION` → 15.

### CAPE accuracy — environmental-noise-aware scoring (measured on the live box)

The "benign scores malscore 10 / malicious" problem was investigated **data-driven** by detonating a battery of benign + do-nothing samples on the real CAPE box (via the REST API — SSH to the box is not available from this workstation) and profiling which signatures fire:
- **Linux guest (`cape1`) fires ZERO signatures on benign input** — the noise is entirely Windows-guest specific.
- **A do-nothing `exit 0` PowerShell script (task 8) still triggers 11 signatures / malscore 6.6.** Those 11 are the pure baseline. A `Write-Host "hello"` one-liner adds `uses_windows_utilities` + `driver_filtermanager`. None of it is the sample.
- The noise is two things: **CAPE's own monitor injecting its analysis DLL** into the sample (`creates_suspended_process`, `reads_memory_remote_process`, `resumethread_remote_process`, `terminates_remote_process`) and **Windows/PowerShell host startup** (`antivm_*`, `antidebug_*`, `queries_locale_api`, `language_check_registry`, mount/drive discovery, …).

Fix in `services/verdict.py`: **`ENVIRONMENTAL_NOISE_SIGNATURES`** (a ~19-name frozenset, curated from the measurements) is excluded from the verdict. The dynamic verdict is computed from **meaningful** (non-noise) signal only — *malicious* needs config/C2/family or a **meaningful** signature at `severity >= 4` (noise tops out at 3); *suspicious* needs ≥1 meaningful signature; a run with only noise is **clean even at malscore 10**. `cape.summarize()` tags each signature `noise: bool`; the Detonation tab shows meaningful signatures prominently and collapses noise into a dimmed "not counted toward the verdict" group, and the malscore ring is coloured by the *verdict*, not the raw score. `ENGINE_VERSION = 9`.

**Calibration (verified against real CAPE reports):** every *trivial* benign file → **clean** (`wintest.ps1`, `exit 0`, `Write-Host`, file-listing, all Linux). A benign-but-suspicious-looking batch that trips `powershell_command_suspicious`/`amsi_enumeration` → **suspicious** (correct — those did NOT fire on trivial scripts, so they're real content signal; forcing them clean would be a false NEGATIVE). Malware shapes (config/C2/high-sev) → **malicious**. Trade-off documented in `verdict.py`: the monitor's own injection is indistinguishable by signature name from real injection and fires on every run, so those names are suppressed and detection leans on config/C2/network/high-sev instead.
